# RAED Robot Design & Optimization Platform

منصة لتكوين وتحسين روبوتات صناعية 6 محاور حسب التطبيق وأداة النهاية، مع CAD وBOM وROM ومحاكاة وحسابات هندسية وملفات تصنيع وتجميع.

## ابدأ هنا — أداة STEP Parts للمكونات الجاهزة

**قبل بحث الروبوتات وبناء قاعدة التطبيق، جهّز أداة `step-parts` المرفقة هنا. استخدمها أثناء تأسيس القاعدة، ثم ضمّن وظيفة البحث وجلب CAD في التطبيق نفسه أثناء تكوين كل تصميم.** لا يكرر المستخدم مرحلة التدريب والبحث المرجعي، لكن مكتبة المكونات وموصلات مصادر CAD والشراء تظل تعمل داخليًا عند الحاجة لمكوّن جديد أو تحديث بياناته.

### الحزمة المضمّنة وطريقة تجهيزها

المصدر هو ملف المستخدم `step-parts.skill`. ملفات الحزمة الأصلية كاملة داخل ملحق آخر هذا المستند، مع بصمة SHA-256 لكل ملف. الحزمة تتضمن:

```text
step-parts/
  SKILL.md
  LICENSE
  agents/openai.yaml
  references/step-parts-api.md
  scripts/download_step_part.py
```

1. أعد كتابة الملفات من كتل الملحق إلى مجلد مشروع داخلي، مثل `tools/step-parts/`، بالأسماء والمسارات الأصلية ودون تغيير المحتوى، ثم راجع بصماتها.
2. اقرأ `SKILL.md` ومرجع API قبل الاستخدام. إذا كانت المنصة تدعم تثبيت Skills بالطريقة الرسمية، استخدم مسارها الموثق؛ وإلا شغّل السكربت كأداة Python داخل المشروع. نسخ الملفات وحده لا يثبت تسجيل Skill في حساب المستخدم.
3. السكربت المرفق يستخدم مكتبات Python القياسية، ولا يحتاج إلى تثبيت CadQuery كي يبحث أو ينزّل؛ قراءة هندسة STEP والتحقق منها تتم بمحرك CAD الموجود بالمشروع.
4. استخدم مضيف API الوارد في الحزمة `https://api.step.parts` وروابط الملفات التي يعيدها، وراجع السلوك الفعلي عند التنفيذ. لا تدّعِ اختبار الخدمة الحية اعتمادًا على هذا المستند وحده.
5. عند تعذّر الشبكة سجّل «تعذّر البحث من هذه البيئة»؛ لا تقل «المكوّن غير موجود». اتبع صلاحيات المنصة، ولا تتجاوز حظر الشبكة أو تكرر طلب تصعيد ممنوع بسبب تعليمات عامة في الحزمة.
6. احتفظ بترخيص الحزمة. ترخيص كود الأداة لا يمنح تلقائيًا حق إعادة توزيع كل ملف CAD تجلبه؛ سجّل شروط كل مصدر CAD على حدة.

### البحث ثم الاختيار ثم التنزيل

ابدأ ببحث محدد؛ مثال تعليمي لمسمار، وليس اختيارًا هندسيًا لروبوت بعينه:

```bash
python tools/step-parts/scripts/download_step_part.py "M3 socket head 12" --limit 10
```

راجع النتائج ومواصفات المكوّن، ثم استخدم المعرّف المؤكد:

```text
python tools/step-parts/scripts/download_step_part.py --id <confirmed_part_id> --download --out-dir CAD/Purchased_Parts
```

استبدل `<confirmed_part_id>` بالمعرّف الفعلي من البحث قبل التنفيذ. السكربت الأصلي عند استخدام نص بحث مع `--download` ينزّل أول نتيجة؛ لذلك لا تعتمد هذا السلوك لاختيار هندسي تلقائي. اجعل الـConfiguration Engine يطابق الموديل والمعيار والأبعاد والخامة وواجهات التثبيت أولًا، ثم ينزّل باستخدام `--id`. لا تستخدم `--all` لتنزيل كتالوج كامل دون حاجة.

### أولوية المصدر والمطابقة

- ابحث في STEP Parts قبل إنشاء بديل هندسي مبسط، باستخدام الموديل الدقيق ثم الأسماء البديلة واسم المصنع والمعيار والمقاس.
- عند غياب نتيجة مطابقة أو تعذّر المصدر، انتقل إلى CAD الرسمي للمصنع أو المورد المعتمد أو كتالوج موثوق مسموح استخدامه. لا تجعل غياب مكوّن من STEP Parts عائقًا وحيدًا للتصميم.
- ترتيب نتائج البحث ليس ترتيب ملاءمة هندسية. لا تستبدل موتورًا أو مخفضًا بموديل «قريب في الاسم»، ولا تعتبر المسمار مطابقًا دون معيار القلاوظ والطول والرأس والخامة أو فئة المقاومة المطلوبة.
- افصل بين المكوّن التجاري المحدد، والـCAD العام المطابق لمعيار قياسي، والغلاف التقريبي. لكل حالة مستوى تحقق ظاهر.
- إذا لم يوجد CAD موثوق، أظهر «CAD غير متاح» مع ما تم البحث فيه. يجوز نموذج غلاف موسوم للمعاينة، لكن لا يُعرض كـCAD أصلي أو مطابقة تركيب متحققة.

### فحص CAD بعد التنزيل

1. تحقّق من SHA-256 المعلن عند توفره. عدم وجود بصمة معلنة ليس تطابقًا تم التحقق منه؛ احتفظ بالبصمة المحلية للتتبع فقط.
2. إذا فشل تطابق البصمة، لا تستخدم الملف؛ السكربت الأصلي قد يكون حفظ الملف قبل اكتشاف عدم التطابق، لذلك اعزله عن الأصول المعتمدة وسجّل الفشل.
3. تحقّق من أن الرد ملف STEP حقيقي يمكن استيراده وليس صفحة خطأ أو مؤشر Git LFS نصيًا. راجع الوحدات والأبعاد الرئيسية وسلامة الأجسام وواجهات التثبيت واتجاهها.
4. تحقق من أمان اسم الملف والمسار، واحفظه داخل مجلد المشروع المحدد. لا تسمح لمسار وارد من مصدر خارجي بالكتابة خارج المجلد.
5. اربط سجل المكوّن بالمعرّف والموديل ورابط CAD ورابط صفحة المصدر وتاريخ التنزيل والبصمة ونتيجة المطابقة والترخيص.
6. خزّن نسخة معتمدة لكل موديل وإصدار وأعد استخدامها مع تكرار Instances داخل التجميع، بدل تنزيل نفس المسمار عشرات المرات.
7. في مرحلة التطوير، بعد إنشاء STEP فعلي استخدم CAD Viewer إذا كانت مهارته متاحة وفق تعليمات الحزمة، وإلا سجّل عدم توفر العرض. داخل التطبيق النهائي اعرض المكون من عارض التطبيق؛ لا تطلب من المستخدم تثبيت بيئة تطوير.

### تغطية كل المكونات التي يحتاجها التصميم

ابدأ من BOM كاملة، واجلب CAD لكل عنصر جاهز له هندسة مؤثرة في التجميع، مثل:

- المحركات والسيرفو والمشغلات، المخفضات والجيربوكسات، الفرامل والإنكودر.
- المحامل والجلب والكوبلنجات والمفاتيح وحلقات التثبيت والجوانات عند الحاجة.
- المسامير والصواميل والورد والدبابيس والأعمدة القياسية والمباعدات.
- الأدوات والجريبر والشعلة والمحولات ومبدلات الأدوات.
- الموصلات وحوامل الكابلات والسلاسل ومانعات الشد والخراطيم والقطع الهوائية أو الكهربائية الداخلة في التصميم.
- وحدات التحكم والدرايف والطاقة والمكونات الموجودة في خلية العمل إذا كانت ضمن نطاق المشروع وتحتاج تمثيلًا هندسيًا.

الكابلات والخراطيم المرنة يُمثّل مسارها وأقطارها وأنصاف أقطار الثني؛ لا تفترض وجود STEP ثابت مناسب لكل وضعية. السوائل واللاصق والمواد الاستهلاكية تُدرج في BOM ووثائق المواصفات، وCAD لها «غير منطبق» بدل إنشاء جسم وهمي.

صنّف كل صف إلى: **CAD مطابق متحقق / CAD قياسي متحقق الأبعاد / غلاف تقريبي / CAD مفقود / CAD غير منطبق**. احسب تغطية CAD للصفوف الفريدة التي تتطلب هندسة فعلًا، وافصلها عن التغطية المرجّحة بالكمية؛ كثرة المسامير لا تخفي غياب CAD للموتور.

أي مكوّن مهم للتركيب بلا أبعاد موثقة يظل مشكلة مفتوحة تمنع اعتبار التجميع مكتملًا هندسيًا. لا تَعِد بتوافر CAD لكل منتج في الإنترنت.

### الربط بالتطبيق والتقارير

ضمّن الوظائف التالية في طبقة الخدمات، مع إدارة مصدر CAD منفصلة عن مصدر الشراء:

```text
search_component_cad(specification)
match_cad_to_component(candidates, verified_component)
download_verify_and_register_cad(selected_id)
find_purchase_sources(component, delivery_market, quantity)
verify_supplier_offer(offer, exact_component)
produce_procurement_report(approved_bom_revision)
```

يحدد الـConfiguration Engine المكوّن المقبول وفق الحسابات والمخزون؛ توفر CAD جميل لموديل ما لا يجعله صالحًا هندسيًا. تغيّر المكوّن أثناء Optimization يحدّث الهندسة والكتلة ومركز الثقل والواجهات والتصادم والـBOM وتقرير الشراء، ويلغي اعتماد الإصدار السابق عند الحاجة.

## تقرير الشراء ومصادر التوريد — مخرج إلزامي

أثناء تصميم الروبوت ابحث عن مصادر فعلية للمكونات المختارة، ثم أخرج تقريرًا مربوطًا بالـBOM والإصدار المعتمد، يوضح **أين يمكن شراء كل عنصر**، وليس مجرد مكان تنزيل CAD.

- **سوق التوريد المطلوب لهذا المشروع هو مصر.** أعطِ الأولوية لشركات وموزعين ومحلات داخل مصر، مع تحديد المدينة والعنوان التجاري المعلن عند توفره، وسعر بالجنيه المصري. اسأل عن محافظة التسليم عند الحاجة لحساب الشحن، ولا تعِد سؤال المستخدم عن البلد بعد تحديده.
- فرّق بين «مخزون موجود داخل مصر»، و«مورد داخل مصر يجلبه بطلب استيراد»، و«مورد خارجي يشحن إلى مصر». المتجر الأجنبي الذي يشحن إلى مصر ليس موردًا محليًا.
- إذا لم تجد الموديل المطلوب محليًا، سجّل «لم يُعثر على مصدر محلي موثق بتاريخ البحث»، ثم اعرض بدائل الاستيراد في قسم منفصل مع قابلية الشحن إلى مصر وشروطها إن كانت معلنة. لا تساوِ عدم العثور مع إثبات انعدام التوفر في مصر.
- بلد المورد وموقع المخزون وبلد تصنيع المكوّن حقول مختلفة؛ المورد المصري لا يعني أن المكوّن صناعة مصرية. لا تستبدل موديلًا معتمدًا بآخر محلي دون إعادة التحقق الهندسي.
- فضّل المصنع والموزع المعتمد، ثم بائعًا يمكن التحقق منه. لا تصف بائعًا بأنه معتمد دون مصدر.
- فرّق بين صفحة منتج، عرض بيع بسعر، توافر مخزون مؤكد بتاريخ، وعرض سعر يحتاج مراسلة. لا ترسل مراسلات أو طلبات شراء تلقائيًا.
- اعرض مصدرًا أساسيًا وبديلًا عند توفرهما. إذا لم يوجد مصدر موثق، سجّل النقص ولا تختلق رابطًا أو سعرًا أو رقم هاتف.
- عند قيد «المخزن فقط»، اعرض الكمية الموجودة والموقع الداخلي إن توفرا، واعتبر روابط الشراء معلومات لإعادة التوريد لا موافقة على استخدام موديل خارجي.

أعمدة التقرير المطلوبة:

| المجموعة | البيانات |
|---|---|
| تعريف الجزء | رقم BOM، رقم الجزء الداخلي، الإصدار، الاسم، المصنع، الموديل، المعايير والمقاسات |
| الكمية | كمية BOM والوحدة، عدد العبوات إذا كان البيع بالعبوة، المخزون الداخلي والكمية المطلوب شراؤها |
| CAD | اسم الملف والمسار، المصدر والرابط، حالة المطابقة، البصمة، تاريخ التحقق |
| مكان الشراء | اسم المورد المصري والمدينة والعنوان المعلن ورابط المنتج؛ ومورد الاستيراد في قسم منفصل عند الحاجة |
| التواصل | بريد أو هاتف أو قناة تواصل تجارية منشورة عند توفرها، دون تخمين |
| التوافر | حالة المخزون أو «يتطلب عرض سعر»، الكمية المتاحة إن ظهرت، تاريخ التحقق ومصدره |
| السعر | سعر الوحدة أو العبوة، العملة، الحد الأدنى للطلب، الضرائب والشحن عند معرفة كل منها |
| التسليم | مهلة التوريد المعلنة وإمكان التسليم لبلد المستخدم إذا تم التحقق منه |
| البدائل | المورد البديل أو الموديل البديل، مع تمييز الاستبدال الهندسي الذي يحتاج إعادة تحقق |
| القرار | مصدر مفضل مع سبب واضح، ونواقص البيانات أو قيود إعادة توزيع CAD |

عملة عرض التقرير الأساسية **الجنيه المصري EGP**. احتفظ بالسعر الأصلي والعملة للمصدر الخارجي، واعرض التحويل فقط بسعر صرف موثق ومؤرخ. لا تجمع العملات قبل تسجيل سعر التحويل وتاريخه، ولا تعامل الشحن أو الضريبة أو الجمارك غير المعروفة كصفر. افصل سعر الجزء عن تكلفة وصوله لمصر، ولا تخمّن نسبة ضرائب أو جمارك دون تصنيف ومصدر صالحين. افصل تكلفة الأجزاء المعروفة عن إجمالي غير مكتمل.

أضف إلى تقرير المورد المصري، عند توفر بيانات منشورة: رقم الهاتف أو واتساب التجاري، رابط موقعه أو صفحة البيع الفعلية، المدينة، الضمان وخدمة ما بعد البيع، وإمكانية إصدار فاتورة وفق ما يعلنه المورد. لا تختلق أي وسيلة تواصل أو تزعم اعتماد المورد دون دليل. قدّم التقرير للمستخدم بالعربية، مع إبقاء أسماء الموديلات وأرقام الأجزاء كما هي.

صدّر **Procurement_Report.xlsx** و**Procurement_Report.html** قابلًا للعرض والطباعة، مع روابط مباشرة. أضف **CAD_Component_Register.csv** لتتبع الملفات، وملخص تغطية CAD ومصادر الشراء والنواقص. تتطابق أرقام الأجزاء والكميات مع BOM المعتمدة. قبل إصدار الملفات، راجع بيانات التوفر والأسعار القديمة أو وسمها بأنها تحتاج تحديثًا؛ احتفظ بالمصادر وتواريخها في لقطة الإصدار.

## التعليمات الأساسية للمنفّذ

ابنِ برنامجًا بسيطًا للمستخدم، هدفه إنتاج تصميم روبوت 6 محاور ومخرجاته الهندسية. هذا الملف يحدد المنتج المطلوب؛ ملف تثبيت المكتبات السابق مرجع داخلي للتطوير فقط. لا تعرض أسماء المكتبات أو خطوات التثبيت للمستخدم داخل البرنامج.

المطلوب ليس واجهة شكلية أو جسمًا ثلاثي الأبعاد للعرض فقط. المطلوب أجزاء CAD منفصلة وتجميع مترابط وقوائم مشتريات وتصنيع ورسومات ثنائية الأبعاد وتعليمات تجميع وBOM، كلها مشتقة من نفس بيانات التصميم.

ابدأ بتقييم كادات حقيقية لروبوتات ذات ستة مفاصل دورانية، ثم حوّل المعرفة المستخلصة إلى عائلة أو مجموعة صغيرة من القوالب البارامترية التي تغطي التطبيقات المستهدفة. عدد القوالب يحدده التحليل، ولا يكفي قالب واحد إذا لم يغطِّ المتطلبات. أبقِ الواجهة بسيطة، واحتفظ بالحسابات والتفاصيل الهندسية داخل التطبيق.

## أ. مرحلة تأسيس داخلية قبل بناء التطبيق

هذه المرحلة مطلوبة قبل تطوير مولّد التصميم النهائي، وليست شاشة أو خطوة يكررها مستخدم التطبيق. المقصود بـ«يتمرّن على الكادات» هو تحليلها، إعادة بناء نماذج بارامترية قابلة للتحقق منها، واستخلاص قواعد تصميم. لا تدّعِ تدريب نموذج لغوي أو Fine-tuning لمجرد تنزيل ملفات CAD.

### أ-1. فهم احتياج Raedbots

- ابحث في الموقع الرسمي https://www.raedbots.com/ والمصادر الرسمية المتاحة عن منتجات الشركة وتطبيقاتها ومجالات عملها.
- فرّق بين معلومات منشورة موثقة، واستنتاجات، ومعلومات لا تُعرف إلا من الشركة. لا تنسب للشركة قدرة تصنيع أو تطبيقًا أو حمولة دون دليل.
- حوّل النتائج إلى نطاق تصميم أولي: التطبيقات المناسبة، الحمولة والوصول المتوقعان، ظروف العمل، التصنيع والصيانة وتوفر المكونات.
- اجمع من المستخدم فقط المعلومات المهمة التي لم تحسمها المصادر، مثل قدرات الورشة الفعلية والميزانية والموردين المفضلين. لا تعتمد افتراضات البحث كمتطلبات نهائية للمشروع.

### أ-2. البحث عن روبوتات 6 محاور وكادات فعلية

- ابحث عن عدة روبوتات وتجمعات فعلية ذات صلة بنطاق الشركة. ابدأ بمواقع الشركات المصنعة والمشروعات المفتوحة، ثم مستودعات CAD الموثوقة.
- سجّل لكل مرجع: الموديل، مصدر CAD، تاريخ التنزيل، الترخيص أو شروط الاستخدام، الوحدات، صيغة الملف، الأجزاء الموجودة، والمستندات الفنية المتاحة.
- صنّف المرجع: تجميع تفصيلي / نموذج خارجي للتكامل / Mesh للعرض / رسم وصفي. ملف STEP خارجي لا يثبت وجود تفاصيل تصنيع أو محركات أو محامل داخله.
- قيّم ملاءمة كل مرجع للشركة وفق التطبيق والحمولة والوصول والدقة والسرعة والصلابة وقابلية التصنيع والتوريد والصيانة وجودة بياناته. لا تملأ البيانات الناقصة بقيم مخترعة ولا تمنحها درجة مؤكدة.
- استخدم ما تسمح به شروط المصدر. إتاحة CAD للتنزيل لا تعني تلقائيًا جواز نسخه تجاريًا أو إعادة توزيعه ضمن التطبيق. سجّل حدود الاستخدام وافصل المرجع التعليمي عن الأصول المسموح تضمينها.
- اختر مرجعًا أو عدة مراجع متكاملة؛ لا تخلط أذرعًا ومعاصم وواجهات من روبوتات مختلفة دون إعادة تحليل التوافق.

### أ-3. التحليل الهندسي العميق

افتح الملفات واختبرها فعليًا. حلّل الوحدات، سلامة الأجسام، شجرة التجميع، المحاور الستة وأطر الإحداثيات، أطوال الوصلات وإزاحاتها، حدود المفاصل، الوصول، وحركة المعصم. استنتج المحاور من الهندسة والوثائق وراجعها؛ لا تفترض أن STEP يحتوي علاقات حركة أصلية.

حلّل واجهات الربط، الثقوب، الأعمدة، المحامل، أماكن المشغلات والجيربوكسات، توجيه الكابلات، مساحات الأدوات، ترتيب التركيب، التجميعات الفرعية، والتمييز بين الشراء والتصنيع. احسب الحجم والكتلة ومركز الثقل والعطالة فقط بالبيانات والخامات اللازمة، وبيّن الافتراضات.

لا تستنتج الحمولة المسموحة أو دقة التكرار أو العمر التشغيلي من الشكل الخارجي وحده. اربط هذه الخصائص بمواصفات موثقة وحسابات أو اختبارات مناسبة. افصل بين المعلومة المقاسة من CAD والمعلومة الواردة من المورد والتقدير الهندسي.

### أ-4. بناء القاعدة الداخلية واختبارها

قبل بناء واجهة المنتج النهائية، أنشئ داخليًا:

- قوالب CAD بارامترية مرخصة أو مصممة من جديد، ذات أرقام أجزاء وواجهات ربط محددة.
- مكتبة مكونات مشتراة تربط الموديل بمواصفاته وCAD وواجهاته ومصدر بياناته.
- قواعد وأبعاد وحدود تصميم، وآلية اشتقاق باقي الأبعاد، وفحوص صحة وتداخل.
- قوالب BOM ورسومات 2D وتسلسل تجميع متوافقة مع القوالب الهندسية.
- حالات اختبار مرجعية للحركة والوصول والكتل والواجهات، موثقة بما يمكن التحقق منه.

أعد بناء نموذج مرجعي مسموح استخدامه، وقارن الأبعاد والواجهات والمحاور والمخرجات مع المرجع. اختبر تغييرات صغيرة وكبيرة داخل نطاق القالب وتحقق من استمرار صحة الأجزاء والتجميع. عند نقص تفاصيل المرجع، سجّل الفجوة وصمّم الجزء الناقص هندسيًا؛ لا تصفه بأنه نسخة مستخرجة من المرجع.

لا تعتبر القاعدة جاهزة إذا كانت مجرد صور أو ملفات مكدّسة. المطلوب تحويل المعرفة إلى كود وبيانات وقواعد واختبارات يستخدمها التطبيق فعليًا.

### أ-5. ما الذي يظهر في التطبيق؟

البحث والمقارنات والتحليل التدريبي مراحل تطوير داخلية. لا تطلب من المستخدم اختيار «ملف مرجعي» أو قراءة تقارير البحث قبل كل تصميم. احتفظ بالمصادر والتراخيص ونتائج الاختبار داخليًا، وبأي إشعارات ترخيص واجبة، ولا تربط وظائف التطبيق بمسارات ملفات مؤقتة أو محادثة سابقة.

المستخدم يرى مواصفاته، التصميم، النتائج التي يحتاج لاتخاذ القرار، التعديلات، الاعتماد والملفات. المكونات التي تحتاج اختيارًا أو بيانات غير متحققة تظهر بوضوح؛ إخفاء تعقيد التطوير لا يعني إخفاء نقص التصميم.

## ب. رحلة المستخدم بعد اكتمال التأسيس

**متطلبات المشروع ← تصميم مقترح داخل خلية العمل ← ROM وفحوص الوصول والتصادم ← تعديل وتحسين ← اعتماد إصدار محدد ← توليد وتسليم الملفات.**

التطبيق يجمع المدخلات بأسئلة قصيرة متتابعة حسب نوع المهمة، ويحفظ الإجابات. لا يعيد سؤال المستخدم عن بيانات سبق إدخالها إلا إذا تعارضت أو تغيّر نطاق المشروع.

| مجموعة المدخلات | البيانات المطلوبة بحسب التطبيق |
|---|---|
| العملية | Pick & Place، مناولة ماكينة، لحام، تجميع، أو مهمة أخرى؛ وصف دورة العمل وأداة التنفيذ |
| الحمل | كتلة قطعة العمل ووزن الأداة منفصلين، مركز الثقل وأبعادهما، العطالة إن توفرت، وقوى أو عزوم العملية |
| الوصول | نقاط العمل واتجاه الأداة عندها، نقاط الالتقاط والوضع والاقتراب، الارتفاعات والمدى المطلوب؛ ليست قيمة نصف قطر فقط |
| خلية العمل | الأبعاد، موضع القاعدة واتجاهها وطريقة التثبيت، الماكينات والطاولات والعوائق والمناطق الممنوعة |
| الأداء | زمن الدورة، السرعة والتسارع، الدقة المطلقة ودقة التكرار كل على حدة، عدد ساعات العمل ودورة التشغيل |
| التصنيع | العمليات المتاحة، الخامات، سماكات أو مقاسات متاحة، قيود الماكينات والتجميع والصيانة |
| الشراء | الميزانية، بلد التوريد، الماركات أو المكونات المفروضة، حدود الطاقة ونظام التحكم عند الحاجة |
| البيئة | حرارة وأتربة ورطوبة وحماية مطلوبة، ومتطلبات تشغيل خاصة حسب المهمة |
| هدف التحسين | أصغر حجم، أقل وزن، أقل تكلفة، أكبر وصول، زمن دورة أقصر، أو أولوية متوازنة |

يجوز إنشاء Concept بافتراضات معلنة عند نقص بيانات. حدد أي معلومة تمنع اختيار المشغلات أو التحقق من الأداء أو إخراج حزمة نهائية؛ لا تسأل عن كل شيء في صفحة واحدة ولا تعتمد التصميم نهائيًا بمدخلات ناقصة مؤثرة.

### ب-1. المدخلات الأساسية التي يحددها المستخدم

هذه القائمة مطلوبة صراحةً في واجهة إدخال المواصفات، بالإضافة إلى بيانات المهمة والخلية المذكورة أعلاه:

| المدخل | تعريفه داخل التطبيق |
|---|---|
| الحمولة | كتلة قطعة العمل بالكيلوغرام، مع وزن الأداة ومركز الثقل منفصلين وبيان الحمل الكلي |
| مدى الوصول | المسافة المطلوبة ونقاط العمل واتجاهات الأداة في إحداثيات الخلية |
| زمن الدورة | الزمن المستهدف للدورة الكاملة بالثانية، شامل الاقتراب والإمساك والانتظار والعودة وفق المهمة |
| نوع الأداة | فئة الأداة المطلوبة ووظيفتها؛ موديل ثابت إن حدده المستخدم أو بدائل مسموحة |
| دقة الحركة | أقصى خطأ موضع بالملليمتر وخطأ اتجاه بالدرجات عند الأداة، مع تحديد الظروف المطلوبة |
| التكرارية | أقصى تشتت مسموح عند تكرار الوصول للوضعية نفسها، منفصلًا عن الدقة المطلقة |
| أقصى وزن للروبوت | حد كتلة الروبوت، مع بيان ما يشمله: القاعدة والمشغلات والكابلات والأداة أو بدونها |
| تكلفة التصنيع | سقف الميزانية والعملة والكمية المنتجة؛ فصل تصنيع الأجزاء عن تكلفة الشراء والتجميع والتشطيب وتكاليف التجهيز |
| أقصى عزم مسموح | حد لكل محور عند الحاجة؛ N·m عند عمود الموتور أو خرج الجيربوكس، مستمر وذروة ومدة الذروة. قوة/عزم العملية الخارجية حقل مستقل |
| السرعة المطلوبة | سرعة TCP الخطية والزاوية، وحدود سرعات المفاصل عند وجودها؛ مع التسارع المطلوب أو حدوده |
| نوع المادة | خامة محددة أو قائمة خامات مسموحة لكل مجموعة أجزاء؛ لا تفرض خامة واحدة على كل الروبوت تلقائيًا |
| طريقة التصنيع | العمليات المسموحة والمتاحة لكل مجموعة أجزاء، مثل CNC أو الصاج أو الطباعة، مع حدود المعدات ذات الصلة |

لكل قيمة مهمة: الوحدة، هل هي قيد إلزامي أم هدف مفضل، وهل هي ثابتة أم قابلة للاختيار ضمن حدود. لا تُخفِ حقول طلبها المستخدم؛ اعرضها بصورة منظمة مع شرح قصير وأمثلة عند الحاجة.

إذا تعارضت المتطلبات، مثل دورة أسرع من الممكن ضمن السرعة والتسارع أو وزن أقل من التصميم القابل للتصنيع، اعرض التعارض واقترح بدائل دون تعديل المتطلبات تلقائيًا.

الدقة والتكرارية المستهدفتان ليستا ناتج حل IK فقط. تقديرهما يحتاج بيانات الخلوص والمرونة والإنكودر والتحكم والمعايرة، وقد يحتاج اختبارًا فعليًا. اعرض مستوى الدليل المتاح ولا تعلن تحقيقهما من شكل CAD وحده.

### ب-2. المتغيرات التي يختارها النظام ويحسّنها

النظام يحاول اختيار القيم التالية آليًا ضمن القوالب ونطاق التصميم المتحقق منه، مع السماح للمستخدم بتثبيت أي اختيار أو تغييره:

| متغير التصميم | طريقة الاختيار والقيود المرتبطة |
|---|---|
| أطوال الوصلات | لتحقيق نقاط العمل واتجاهاتها مع تقليل الحجم والعزوم وفق الهدف |
| أقطار الوصلات | للأجزاء الدائرية؛ ولغير الدائرية اختَر عرض وارتفاع المقطع وفق الصلابة والتصنيع |
| سماكات الأجزاء | ضمن حدود الخامة والتصنيع والأحمال والتشوه والواجهات |
| نوع المادة | من الخامات المسموح بها، وفق خواص موثقة وتكلفة وتوفر؛ احترم الخامة التي ثبتها المستخدم |
| المحركات | موديلات فعلية بناءً على العزم والسرعة المستمرين والذروة ودورة التشغيل والعطالة والأبعاد |
| نسب التخفيض | نسب تجارية متاحة، مع الكفاءة والخلوص وحدود العزم والسرعة والعطالة المنعكسة |
| المحامل | نوع ومقاس فعليان وفق الحمل الشعاعي والمحوري والعزم والسرعة والعمر المطلوب وترتيب التثبيت |
| ترتيب المكونات | داخل الحيز المتاح، مع الوصول للتجميع والصيانة ومنع التداخل وتقليل الكتلة المتحركة |
| حجم القاعدة | وفق التثبيت وعزوم رد الفعل والاستقرار والحيز المسموح |
| شكل الذراع | اختيار عائلة مقاطع وأشكال بارامترية قابلة للتصنيع وتحسين أبعادها؛ لا تفترض حرية شكل غير محدودة |
| مسار الكابلات | مسار وأماكن تثبيت تسمح بحركة المحاور، وتراعي أقطار الكابلات وأنصاف أقطار الثني والالتواء المسموح |
| أداة النهاية المناسبة | اختيار موديل أو تصميم أداة مناسب للمهمة والقطعة والقوى، مع وزنها وواجهتها واحتياجاتها من طاقة أو هواء |

إذا لم تكن بيانات كابل أو محمل أو جيربوكس متاحة، سجّل ما يحتاج تحققًا بدل تخمين حدود تشغيله. مراجعة حركة الكابلات تستخدم مدى الحركة الفعلي، وليس وضعية واحدة فقط.

### ب-3. حل التداخل بين اختيارات المستخدم والنظام

الخامة والأداة وطريقة التصنيع وغيرها لها ثلاث حالات واضحة:

- **ثابت:** يستخدم النظام القيمة أو الموديل المحدد ولا يستبدله أثناء التحسين.
- **اختيار من قائمة:** يبحث النظام فقط بين البدائل التي سمح بها المستخدم.
- **اختيار تلقائي:** يقترح النظام اختيارًا موثقًا داخل حدود المهمة والميزانية، ويعرضه للمراجعة.

مثال: يحدد المستخدم أداة «شفط» كوظيفة، ويختار النظام الموديل وعدد الكؤوس والمقاسات المناسبة. إذا حدّد المستخدم موديل أداة بعينه، يصبح هذا الموديل ثابتًا وتُصمّم واجهة الروبوت له. اختيار الخامة آليًا لا يلغي طريقة التصنيع المسموحة.

### ب-4. حلقة التصميم والتحسين

1. ترجم المدخلات إلى قيود وأهداف ووحدات متسقة.
2. اختر القالب أو القوالب المناسبة من القاعدة الداخلية، وحدود المتغيرات ومجموعة المكونات التجارية المرشحة.
3. ولّد مرشحين لأطوال الوصلات والمقاطع والسماكات والخامات وترتيب المكونات.
4. اختبر الوصول واتجاهات الأداة والتداخل والمسار وزمن الدورة، ثم أحمال المحاور وتقديرات الصلابة حسب مستوى النموذج المتاح.
5. اختر الأداة والمشغلات والتخفيض والمحامل، وحدّث كتلها وأبعادها ومراكز ثقلها. أعد الحساب لأن تغيير مكون قد يغير متطلبات باقي المحاور.
6. أعد توليد CAD وفحوص التركيب والتصنيع ومسار الكابلات وتقدير التكلفة.
7. كرر حتى تصل لحل قابل للتحقق ضمن شروط توقف معلنة أو تبيّن عدم وجود حل صالح؛ لا تستخدم دورة بحث غير محدودة.
8. اعرض للمستخدم أفضل البدائل الصالحة المتاحة وجدول **المطلوب / المحسوب أو المقدّر / مصدر التحقق / مستوفى أو غير مستوفى أو غير محسوم**.
9. اسمح بالتعديل اليدوي وإعادة التحسين، ثم اطلب اعتماد الإصدار قبل إصدار الحزمة النهائية.

التقدير الأولي للصلابة أو التكلفة ليس اعتمادًا نهائيًا. إذا كانت بيانات الأسعار أو خواص المواد أو أداء المكونات ناقصة، يظل تقييم ذلك القيد غير محسوم، ولا تُعامل القيمة المجهولة كصفر أو كشرط مستوفى.

## ج. خلية عمل افتراضية + ROM

المطلوب الوظيفتان معًا:

### خلية العمل الافتراضية

- اعرض الروبوت داخل مساحة ثلاثية الأبعاد بمقياس ووحدات واضحة.
- أضف الأرضية، الطاولات، الماكينات، الحوامل، حدود الخلية، العوائق ومناطق الحظر كأجسام مبسطة أو CAD مستورد.
- اسمح بتحريك موضع قاعدة الروبوت واتجاهها وإدخال إحداثيات دقيقة، وإضافة مواضع العملية واتجاهات الأداة ومسار المهمة.
- اعرض الأداة وقطعة العمل المحمولة عند فحص التداخل؛ اختبر اصطدام الروبوت بنفسه وبالبيئة.

### ROM — Range of Motion

- اعرض حدود حركة J1–J6، والغلاف أو السحابة التي يمكن لنقطة الأداة TCP الوصول إليها ضمن هذه الحدود.
- ميّز بين الوصول إلى موضع فقط، والوصول إلى الموضع مع اتجاه الأداة المطلوب، والوصول الخالي من التصادم، وإمكان تنفيذ المسار كاملًا.
- لوّن نقاط المهمة: قابلة للوصول / غير قابلة / تتطلب تغيير وضعية أو فحصًا إضافيًا. اعرض سبب الفشل كحد مفصل أو اتجاه غير ممكن أو اصطدام أو قرب تفرد حركي.
- استخدم الحركة العكسية المناسبة، وراجع نتائجها بالحركة الأمامية، وابحث في حلول أو بدايات متعددة قبل الجزم بعدم إمكان نقطة.
- عند اختبار المسار، تحقق من الوضعيات الوسيطة وحدود المفاصل والسرعة والتسارع، وليس نقطتي البداية والنهاية فقط.
- لا تعتبر سحابة عيّنات دليلًا رياضيًا على كل حدود الوصول. وضّح دقة أخذ العينات وهوامش فحص التصادم، ولا تصف فحصًا متقطعًا بأنه ضمان مستمر.
- أعد الحساب عند تغيير الأبعاد أو موضع القاعدة أو الأداة أو الحمل أو البيئة. اعرض «جارٍ التحقق» بدل إبقاء نتائج قديمة تبدو صالحة.

## د. التعديل والتحسين Optimization

المستخدم يستطيع تكبير أو تصغير الروبوت، زيادة أو تقليل طول وصلة، تعديل سماكة أو مقطع، تغيير موضع القاعدة، أو استبدال مكون مشترى. أتح هذه التعديلات بحقول ومنزلقات وأوامر نصية، مع معاينة سريعة ثم حساب هندسي محدث.

التكبير والتصغير تغيير هندسي بارامتري وليس مجرد Scale للشكل. لا تكبّر موتورًا أو محملًا أو مسمارًا قياسيًا نسبيًا؛ اختر مقاسًا تجاريًا حقيقيًا وأعد تصميم الواجهة له. زيادة الحمولة تعيد حساب الكتل والعزوم والمكونات والصلابة بحسب النموذج المتاح، ولا تغيّر خانة الحمولة فقط.

- يستطيع المستخدم تثبيت متغيرات مثل الموتور الحالي أو مكان القاعدة أو حجم الخلية، وترك متغيرات أخرى للتحسين ضمن حدود معلنة.
- افصل أهداف التحسين عن القيود الملزمة: مثال «أقل حجم» مع ضرورة خدمة جميع نقاط المهمة والاحتفاظ بالحمولة وزمن الدورة.
- قدّم بدائل قليلة قابلة للمقارنة: مدمج / اقتصادي / أداء أعلى عندما توجد حلول مناسبة، أو أفضل البدائل الممكنة مع سبب الاختلاف.
- اعرض قبل/بعد للأبعاد والوزن والوصول وتغطية نقاط العمل وتقديرات التكلفة وعزوم المحاور والمكونات التي تغيّرت، مع حالة تحقق كل مؤشر.
- استخدم حسابات هندسية وأداة بحث أو Optimization مناسبة لتقييم المرشحين؛ دور AI تفسير الطلب واقتراح البدائل، وليس اختراع نتائج الأداء.
- لا تدّعِ «الحل الأمثل عالميًا» دون إثبات. بيّن نطاق المتغيرات والقيود ومعيار المفاضلة ومدى التحقق من النتيجة.
- إذا لم يوجد حل صالح ضمن القيود، اذكر المتطلبات المتعارضة واقترح ما يمكن تغييره بدل إخراج تصميم شكلي.
- وفّر Undo/Redo، حفظ الإصدارات ومقارنتها والعودة لإصدار سابق.

### د-1. أمثلة أهداف التحسين والقيود

الأمثلة التالية متطلبات وظيفية للحسابات؛ الأرقام التوضيحية لا تتحول تلقائيًا إلى مواصفات مشروع المستخدم.

**تقليل الوزن:**

```text
Minimize robot_mass
Subject to:
  validated_payload_capacity >= required_payload
  max_task_deflection <= allowed_deflection
  min_safety_factor >= required_safety_factor
  all_required_task_poses_and_paths_are_feasible
```

إذا كانت حمولة المستخدم المطلوبة 10 kg، يستبدل `required_payload` بالقيمة المناسبة وفق تعريف الحمل المتفق عليه، مع احتساب الأداة والأحمال الخارجية بصورة منفصلة ومتسقة. لا تضاعف وزن الأداة في الحساب. نسبة الأمان تُعرّف لكل نمط فشل ومادة وحالة تحميل ذات صلة؛ لا تكفي قيمة عامة غير موثقة. إذا لم يتوفر تحليل التشوه أو الأمان المناسب، اعرض القيد كغير متحقق وليس ناجحًا.

**تقليل التكلفة:**

```text
Minimize total_cost
Subject to:
  components_are_approved_and_available
  parts_are_manufacturable
  torque_speed_and_task_constraints_are_satisfied
```

عرّف `total_cost` حسب نطاق الميزانية: شراء وتصنيع وتجميع وتشطيب وتجهيز موزع على كمية الإنتاج عند انطباقه. كل سعر له عملة وتاريخ ومصدر أو تصنيف تقديري. «معتمد» يعني مدرجًا في قائمة المكونات المقبولة من الشركة أو المستخدم، وليس شهادة اعتماد يختلقها البرنامج. توفر المخزون يُراجع بتاريخ معلوم؛ اختيار موديل من كتالوج لا يثبت توفره للشراء الآن.

**تقليل زمن الدورة:**

```text
Minimize cycle_time
Subject to:
  motor_and_gearbox_speed_limits
  continuous_RMS_and_peak_torque_limits
  collision_clearance >= required_clearance
  singularity_margin >= required_margin
  deflection_and_vibration_limits
  process_speed_and_acceleration_limits
```

احسب زمن الدورة على مسار المهمة مع أوقات التشغيل والإمساك والتوقف؛ لا تستخدم المسافة مقسومة على السرعة القصوى فقط. افحص منحنى العزم/السرعة وحدود العزم المستمر وRMS والذروة ومدة الذروة حسب بيانات المشغلات. قيود الاهتزاز لا تُعتبر متحققة إذا لم يوجد نموذج مناسب أو بيانات اختبار؛ تُوسم غير محسومة.

### د-2. تصميم جسم واحد لأداتين أو تصميمات منفصلة

أضف اختيارًا واضحًا: **نفس الروبوت يخدم الأداتين** / **تحسين كل مهمة أو Configuration بشكل مستقل**.

مثال توضيحي لأداتين: Gripper بكتلة 1.5 kg وWelding Torch بكتلة 3 kg. لا تعتبر هذه أرقام الموديلات النهائية.

التقدير الأولي `workpiece_mass + heaviest_tool_mass` يصلح فقط إذا كانت كتلة قطعة العمل المحمولة نفسها موجودة مع كلتا الأداتين. في الحالة العامة، لكل سيناريو:

```text
attached_mass(case) = tool_mass(case)
                    + adapter_or_toolchanger_mass(case)
                    + carried_workpiece_mass(case)
                    + other_attached_masses(case)
required_attached_mass_envelope = max_over_cases(attached_mass(case))
```

قد تكون قطعة اللحام ثابتة على الطاولة وليست محمولة بواسطة الشعلة؛ عندها لا تضف وزنها إلى وزن الأداة المحمولة. أضف قوى العملية وردود فعل الكابل عند توفر بياناتها، ولا تحولها إلى كتلة مفترضة دون نموذج.

فحص الوزن الأولي لا يكفي لاختيار المحركات. احسب لكل محور غلاف العزم والسرعة والأحمال على المحامل والتشوه عبر كل وضعيات ومسارات كل أداة، مع مركز الثقل وعطالة الأداة والقطعة. أداة أخف بمركز ثقل أبعد قد تكون أسوأ على محور معين من أداة أثقل. لا تفترض أن كل القيم القصوى تحدث في وضعية واحدة.

عند استخدام جسم واحد، يجب أن يستوفي جميع السيناريوهات المطلوبة. عند السماح بروبوتات أو Configurations مختلفة، حسّن كل حالة منفصلة وبيّن الاختلاف في الجسم والمكونات والتكلفة والملفات. لا تصف تغيير CAD للجسم بأنه تبديل أداة فقط.

### د-3. تقييم Gripper مقابل Welding Torch

| الجانب | Gripper | Welding Torch |
|---|---|---|
| المهمة | التقاط وحمل ووضع قطعة | تتبع مسار لحام |
| المدخلات المهمة | كتلة القطعة ومركز ثقلها، شكلها وسطح الإمساك وقوة القبض واتجاهاتها | خط اللحام وTCP وزاوية الشعلة والمسافة المطلوبة وسرعة العملية |
| أداء الحركة | السرعة والتسارع وزمن الدورة وتكرارية الوضع | انتظام سرعة المسار ودقة التتبع وإمكان بلوغ الوضعيات |
| الوصول والتصادم | الوصول إلى الالتقاط والوضع والاقتراب مع القطعة المحمولة | الوصول إلى خط اللحام مع جسم الشعلة والفوهة وزواياها والكابلات |
| توصيلات العملية | طاقة أو هواء وإشارات الغلق/الفتح | السلك والغاز والكابلات وتنسيق الحركة مع مصدر اللحام |

افصل بين **تصميم الروبوت ميكانيكيًا** و**تخطيط المهمة والتحكم في العملية**. الاختيار الميكانيكي يُقيّم باستخدام المسار المطلوب، لكن نجاحه لا يعني أن نظام اللحام أو برنامج تشغيل المصنع جاهز. اتصال مصدر اللحام الفعلي وبرمجة التشغيل الصناعية ليسا جزءًا تلقائيًا من النسخة الأولية.

في حالة الشعلة، افحص خط اللحام بكامل اتجاهاته وحالات الاقتراب والابتعاد؛ قد تصل الأداة إلى نقطة لكن لا تصل بالزاوية المطلوبة أو لا تنتقل لها عبر مسار صالح.

### د-4. اقتراح عدة Configurations ومقارنتها

لكل Configuration، ينتج النظام نتائج منفصلة قابلة للمراجعة:

1. تعريف القالب وأطوال ومقاطع الوصلات وسماكاتها والخامة وترتيب المكونات.
2. الموديلات المختارة للمحركات والمخفضات والمحامل والأداة، وكتلها ومراكز ثقلها.
3. مجال الحركة والوصول وتغطية نقاط المهمة واتجاهاتها.
4. عزم كل محور: الجاذبية والديناميكي وفق النموذج المتاح، المطلوب المستمر أو RMS والذروة، وحدود المكون وهوامشه؛ افصل جانب الموتور عن جانب الخرج.
5. سرعة كل محور والموتور والتحقق من حدود المخفض وزمن الدورة.
6. فحص Singularities باستخدام مقياس معرف مثل أصغر قيمة منفردة لـJacobian أو condition number، مع توضيح تطبيع وحدات الحركة الخطية والزاوية والحدود المستخدمة. لا تستخدم رقمًا سحريًا غير مفسر.
7. تصادم ذاتي ومع خلية العمل والأداة والقطعة، بدقة الفحص وهوامشه المعلنة.
8. الوزن وتقدير التكلفة والحمولة المتحقق منها والتشوه والبيانات غير المحسومة.
9. قائمة القيود المستوفاة وغير المستوفاة وغير المتحقق منها، وأسباب رفض المرشح إن وجدت.

يمكن ترتيب النتائج حسب الوزن أو السعر أو زمن الدورة أو هدف أداء محدد. لا تستخدم وصف «أعلى أداء» دون تعريف مؤشرات الأداء.

### د-5. Pareto Frontier واختيار المهندس

اعرض مخططًا تفاعليًا وجدولًا للبدائل غير المهيمن عليها **داخل مجموعة المرشحين الذين تم تقييمهم**، مع اختيار محورين مثل الوزن والتكلفة، وإظهار زمن الدورة باللون أو في تفاصيل النقطة.

التصميم يهيمن على آخر عندما لا يكون أسوأ في كل الأهداف المقارنة ويكون أفضل في هدف واحد على الأقل، مع توحيد اتجاه أهداف التصغير والتكبير. وضّح أن الجبهة ناتجة عن نطاق البحث الحالي وليست إثباتًا لأمثلية عالمية.

- قيّم الجدوى أولًا: التصميم المخالف لقيد إلزامي لا يدخل جبهة الحلول الصالحة، وإن ظهر في جدول التشخيص فليظهر مرفوضًا وسبب رفضه.
- الحل ذو بيانات أساسية غير متحققة لا يظهر كحل صالح مؤكد؛ ميّزه كمرشح يحتاج استكمال بيانات.
- لا تستخدم أسعارًا وصفية مثل «منخفضة» في حساب جبهة تكلفة عددية. استخدم أسعارًا متسقة وموثقة أو تقديرات موسومة، وافصل غياب السعر عن قيمته.
- لا تُخفِ البدائل خلف نتيجة واحدة. يختار المهندس التصميم أو يثبّت بعض المتغيرات ويعيد البحث، ثم يعتمد إصدارًا محددًا.
- يمكن إظهار ترتيب موزون اختياري، مع أوزان معلنة قابلة للتعديل، لكنه لا يحل محل Pareto Frontier أو فحص القيود.

مثال المستخدم التالي **بيانات توضيحية للواجهة فقط، وليست نتائج حسابات أو أسعارًا فعلية**:

| التصميم | الوزن | مستوى التكلفة | الحمولة المعروضة | زمن الدورة | الوصف التوضيحي |
|---|---|---|---|---|---|
| A | 82 kg | منخفضة | 8 kg | 11.4 s | اقتصادي |
| B | 96 kg | متوسطة | 12 kg | 9.8 s | أسرع من A |
| C | 110 kg | مرتفعة | 15 kg | 8.7 s | حمولة أعلى ودورة أقصر في المثال |

إذا كان قيد المشروع حمولة لا تقل عن 10 kg، فالتصميم A غير مستوفٍ ويُستبعد من الجبهة الصالحة. هذه القيم وحدها لا تثبت أن B أو C صالحان؛ يجب أيضًا فحص المسار وباقي القيود، ولا تُسمَّ مجموعة المثال Pareto Frontier قبل التحقق من الهيمنة والجدوى.

## هـ. اعتماد المستخدم وإصدار الملفات

1. اعرض التصميم المقترح داخل الخلية، ملخص المتطلبات، نتائج ROM وفحوص المهمة، وقائمة المكونات والبيانات غير المحسومة.
2. اسمح بمراجعة التصميم وتعديله عدد المرات اللازمة، ثم اطلب إجراء واضحًا: **«اعتماد هذا الإصدار وإصدار الملفات»**.
3. الموافقة تكون لإصدار محدد من الهندسة والمتطلبات والبيئة والمكونات. احفظ لقطة ثابتة لهذه البيانات وتاريخ الاعتماد.
4. بعد الموافقة، ولّد حزمة CAD والأجزاء المشتراة والمصنّعة ورسومات 2D وتعليمات التجميع والـBOM من الإصدار نفسه، وافحص تطابقها قبل التسليم.
5. يمكن إظهار معاينات قبل الاعتماد، لكن الحزمة النهائية لا تصدر تلقائيًا قبل الموافقة. إذا كشفت عملية التوليد مشكلة تستدعي تغيير التصميم، أصلحها واعرض الإصدار المعدل لاعتماد جديد.
6. أي تعديل مؤثر بعد الاعتماد ينشئ إصدارًا غير معتمد؛ لا تعدّل الحزمة المعتمدة في الخلفية ولا تحافظ على علامة اعتماد لبيانات تغيرت.
7. اعتماد المستخدم للتصميم وإصدار الملفات لا يساوي شهادة سلامة صناعية أو إثبات أداء بالاختبار. حافظ على بيان حالة المراجعة الهندسية للرسومات والنتائج، وافصل حزمة المراجعة أو النموذج التجريبي عن الحزمة المعتمدة للتصنيع وفق حالات القسم 15.

## 1. تجربة المستخدم

واجهة بسيطة داخل مشروع واحد بها ثلاث مناطق، مع خطوات إدخال تدريجية:

1. **بيانات الروبوت:** الحمولة، أقصى وصول، أبعاد أو قيود المساحة، وطريقة التصنيع. أضف اختيار أداة النهاية أو إدخال وزنها وأبعاد واجهتها. وضّح هل الحمولة المدخلة تشمل الأداة أم لا.
2. **خلية العمل وROM:** الروبوت والمعدات والعوائق ونقاط المهمة وغلاف الوصول، مع شجرة الأجزاء والعرض المنفجر وتحريك المحاور.
3. **المراجعة والمخرجات:** مقارنة التعديلات، اعتماد الإصدار، ثم المشتريات والتصنيع ورسومات 2D وتعليمات التجميع وBOM وتنزيل الحزمة الكاملة.

أزرار واضحة: «إنشاء التصميم»، «تعديل وتحسين»، «فحص الحركة والوصول»، «اعتماد التصميم»، «تنزيل الملفات».

المدخلات المتقدمة تظهر تدريجيًا بحسب العملية؛ أي بيانات تؤثر على اختيار المشغلات أو صلاحية المهمة تُطلب قبل الاعتماد. القيم الافتراضية تظهر كافتراضات قابلة للتغيير، وليست متطلبات مؤكدة.

يمكن إضافة مربع أوامر بسيط مثل «زوّد طول الذراع 50 مم». يحوّل الذكاء الاصطناعي الطلب إلى تعديلات على البارامترات والوظائف المحددة، ثم يعرض أثر التعديل. يجب أن تعمل الوظائف الأساسية بالأزرار حتى بدون خدمة AI.

## 2. إنتاج الأجزاء والتجميع

- أنشئ أجزاء CAD صلبة منفصلة، لكل منها رقم جزء واسم وإصدار وخامة وكمية وتصنيف.
- يشمل التصميم، بحسب البنية المختارة: القاعدة، حوامل المفاصل، الذراعين، حوامل المحركات وعلب التخفيض، الأعمدة، الأغطية، وفلانشة أداة النهاية، بالإضافة إلى عناصر التثبيت والمحامل والمكونات المشتراة.
- استخدم نفس تعريف الأجزاء والمحاور وأماكن التثبيت في العرض والحسابات والرسومات والقوائم. لا تولّد كل مخرج ببيانات مستقلة.
- حافظ على أماكن الربط والأبعاد المشتركة أثناء تعديل التصميم، ونبّه إلى أي تعارض أو تداخل.
- اعرض جميع الأجزاء في شجرة تجميع، وميّز بصريًا بين المشترى والمصنّع، مع إمكانية رؤية التفاصيل عند اختيار الجزء.
- وفّر STEP لكل جزء هندسي، وSTEP للتجميع، وSTL عند الحاجة للطباعة ثلاثية الأبعاد. لا تعتبر STL بديلًا عن STEP.
- تعديل مقاس أو جزء يحدّث المخرجات التابعة له. المخرجات القديمة تُعلّم بأنها تحتاج إعادة توليد حتى يكتمل تحديثها.

## 3. فصل المشتريات عن التصنيع

لكل عنصر قرار واحد واضح: **شراء / تصنيع / يحتاج تحديدًا**. الحالة الأخيرة تظهر للمستخدم كي يحسمها، ولا تُخفى داخل القائمة.

### المشتريات

أمثلة: المحركات، الجيربوكسات، المحامل، الإنكودر، الكوبلنج، المسامير، حلقات التثبيت، وأداة النهاية إذا كانت جاهزة. أضف عناصر التحكم والكهرباء المختارة للتصميم إلى الـBOM بفئتها؛ لا تستبعد عنصرًا لمجرد عدم توفر CAD له.

لكل عنصر مشتَرى:

- رقم الجزء الداخلي، الاسم، المصنع، رقم الموديل، المواصفات المطلوبة والكمية.
- المورد أو رابط المنتج ومصدر المواصفات عند توفره.
- ملف CAD الأصلي للموديل المحدد، ورابط مصدره، إذا كان متاحًا ومسموحًا باستخدامه.
- حالة مطابقة الأبعاد وواجهات التثبيت للموديل المختار.
- السعر والعملة وتاريخ السعر إن كان متحققًا منه؛ وإلا اكتب «غير متوفر» دون اختلاق سعر.

إذا لم يتوفر CAD أصلي، استخدم نموذج غلاف مبسّط من الأبعاد المعروفة ووسمه بوضوح بأنه **تمثيل تقريبي**. لا تنسبه للمصنع ولا تعتبره إثباتًا لملاءمة التركيب. لا تنشئ تفاصيل داخلية تخمينية لمكون مشترى.

لا تعتبر موتورًا مناسبًا للحمل بمجرد كتابة قيمته في جدول؛ يجب أن يستند الاختيار إلى حسابات الحمل والسرعة والكتل ونسبة التخفيض والبيانات المتاحة. عندما تكون البيانات ناقصة، يبقى الاختيار مقترحًا للمراجعة.

### التصنيع

لكل جزء مصنّع:

- رقم الجزء والاسم والإصدار والكمية والخامة ومواصفة الخامة إن توفرت.
- طريقة التصنيع: تشغيل CNC، صاج، طباعة ثلاثية الأبعاد أو غيرها.
- الأبعاد العامة والكتلة المحسوبة من الحجم والكثافة المعروفة.
- المعالجة أو التشطيب عند الحاجة، وملاحظات التصنيع.
- رابط STEP ورسم 2D الخاص بنفس الإصدار.

## 4. رسومات 2D

أنشئ رسومات تصنيع للأجزاء المصنّعة، ورسومات تجميع للروبوت والتجميعات الفرعية. المكونات المشتراة لا تحتاج رسومات تصنيع داخلية؛ استخدم رسومات المورد وأبعاد التركيب عند توفرها.

كل رسم جزء يشمل حسب الحاجة:

- المساقط اللازمة، ومنظورًا توضيحيًا، ومقاطع وتفاصيل للأماكن غير الظاهرة.
- الأبعاد اللازمة للتصنيع والفحص، وليس مجرد الأبعاد الخارجية.
- مواضع الثقوب وأقطارها وأعماقها وتوصيف القلاوظ، وأنصاف الأقطار والشطفات.
- المراجع والأبعاد الوظيفية والتفاوتات والملاءمات والخشونة حيث تم تحديدها هندسيًا.
- رقم الجزء والإصدار والخامة والكمية والمقياس والوحدات وخانة عنوان منظمة.

صدّر PDF للقراءة والطباعة، وDXF للهندسة ثنائية الأبعاد المناسبة، خصوصًا الأجزاء المسطحة. لا تعد بتصدير DWG دون محرك يدعمه. إذا كانت هناك حاجة لفرد الصاج، استخدم السمك ونصف قطر الثني وبيانات الثني المعتمدة؛ لا تعتبر إسقاط الجسم فردًا للصاج.

الرسومات تُنشأ أولًا بحالة **مسودة للمراجعة**. لا تضع تفاوتات أو خشونة أو ملاءمات عشوائية حتى يبدو الرسم مكتملًا. أظهر البيانات الهندسية التي لم تُحسم في قائمة مراجعة. تغيير الحالة إلى «معتمد للتصنيع» يتطلب مراجعة بشرية صريحة.

## 5. تعليمات التجميع

جهّز دليل تجميع HTML قابلًا للعرض داخل البرنامج والتصدير للطباعة، مع صور من نفس نموذج CAD:

1. عرض منفجر مرقّم لكل تجميع فرعي.
2. خطوات بالترتيب، توضح الجزء الذي يركب على أي جزء واتجاه دخوله.
3. أرقام الأجزاء والكميات والمسامير والأدوات اللازمة لكل خطوة.
4. إجراءات تركيب المحامل والمحاور والمشغلات وتوجيه الكابلات عند انطباقها على التصميم.
5. عزوم الربط أو مواد التثبيت فقط إذا كانت محددة من مصدر مناسب؛ لا تخمّنها.
6. فحص نهاية كل مجموعة، ثم فحص التجميع النهائي للحركة والتداخل وإمكانية الوصول للمسامير.

العرض المنفجر وحده ليس تعليمات تجميع. يجب مراجعة ترتيب التركيب وإمكانية تنفيذ الخطوات فعليًا. لا تزعم أن نموذج الحركة يعادل إثبات السلامة أو اعتماد تشغيل روبوت حقيقي.

## 6. قائمة المواد BOM

أنشئ BOM هرمية للتجميعات، ونسخة مجمّعة تجمع كميات أرقام الأجزاء المتكررة. استخرج قائمة المشتريات وقائمة التصنيع من هذه الـBOM نفسها.

الأعمدة الأساسية:

| الحقل | الغرض |
|---|---|
| Item / رقم البند | الربط مع ترقيم رسومات التجميع |
| Parent Assembly | التجميع الأب |
| Part Number | رقم الجزء الفريد |
| Revision | الإصدار |
| Description | وصف الجزء |
| Make / Buy | تصنيع أو شراء أو يحتاج تحديدًا |
| Quantity / Unit | الكمية والوحدة |
| Material / Specification | الخامة أو المواصفة |
| Manufacturer / Model | للمكونات المشتراة |
| Mass | عندما تتوفر بيانات حساب موثوقة |
| Supplier / Unit Cost | عند توفر بيانات موثقة |
| CAD / Drawing | روابط الملفات ذات الإصدار المطابق |
| Status / Notes | حالة المراجعة والمعلومات الناقصة |

صدّر Excel وCSV. لا تحوّل الأسعار غير المعروفة إلى صفر، ولا تعرض مجموع تكلفة نهائيًا إن كانت عناصر ناقصة؛ اعرض مجموع الأسعار المعروفة مع بيان النقص. امنع تكرار احتساب التجميع ومكوناته في الإجمالي.

## نطاق النسخة الأولى المتفق عليه — MVP

بعد إتمام مرحلة البحث والتحليل وبناء القاعدة، ابدأ بنطاق محدود واضح:

| العنصر | حدود النسخة الأولى |
|---|---|
| المحاور | 6 محاور دورانية |
| الوصلات | 2 أو 3 مقاسات أو مجموعات مقاسات محددة، مشتقة من التحليل ومختبرة؛ لا تفتح أطوالًا غير محدودة |
| المحركات | 3 موديلات حقيقية معتمدة؛ يختار النظام منها لكل محور، ولا يعني ذلك 3 محركات فقط في الروبوت |
| المخفضات | 3 موديلات محددة، مع نسبها المتاحة وواجهات تركيبها وبياناتها |
| أداة الإمساك | Gripper واحد موثق |
| أداة اللحام | Welding Torch واحدة موثقة |
| واجهة الأداة | Tool flange ثابت موثق؛ يمكن استخدام Adapter محدد عند اختلاف الأداة، ويُحسب وزنه وصلابته وواجهاته |
| الخامات | خامتان محددتان بخواص موثقة |
| التصنيع | طريقة واحدة أو طريقتان فقط، وفق إمكانيات الشركة |

اختَر الأسماء التجارية والمقاسات الفعلية بعد البحث وتحليل احتياج الشركة؛ لا تخترع أرقام موديلات أو اعتمادًا من Raedbots. إذا لم تستطع هذه المجموعة تغطية قيد المستخدم، أظهر عدم وجود حل واقترح توسيع الكتالوج بدل تجاوز القيود سرًا.

### وظائف النسخة الأولى الإلزامية

- CAD Parametric للأجزاء والتجميعات داخل عائلة التصميم المدعومة.
- Forward / Inverse Kinematics.
- Motor sizing ومقارنة متطلبات العزم والسرعة بالمكونات الثلاثة المعتمدة.
- Payload validation ضمن حالات التحميل ومستوى التحليل المتاح، مع توضيح الحالات غير المتحقق منها.
- Tool selection بين الأداتين، أو تقييم جسم واحد لهما وفق اختيار المستخدم.
- Basic collision checking ذاتيًا ومع خلية العمل، مع بيان حدود التقريب وأخذ العينات.
- خلية عمل مبسطة وROM لنقاط المهمة واتجاهاتها.
- فحص قرب Singularities والتحقق الأساسي من السرعات وزمن الدورة لمسار معلوم.
- STEP export للأجزاء والتجميع المعتمد.
- BOM وفصل الشراء عن التصنيع من المصدر نفسه.
- Ranking للـConfigurations وPareto Frontier داخل المرشحين المقيمين.
- تعديل واختيار من الحدود المتاحة، حفظ إصدارات، واعتماد المستخدم قبل إصدار الحزمة المتاحة في هذه المرحلة.

### المرحلة التالية المطلوبة لإكمال المنتج

رسومات 2D التفصيلية للأجزاء والتجميعات، وتعليمات التجميع المصورة والعرض المنفجر، واكتمال حزمة الملفات المطلوبة في الأقسام السابقة، تظل متطلبات قائمة. نفّذها بعد استقرار النموذج والـBOM، ولا تحذفها من نطاق المنتج النهائي بسبب تضييق النسخة الأولى.

بيّن بوضوح ما اكتمل في كل إصدار. لا تعرض زر تصدير رسومات أو دليل تجميع على أنه يعمل إذا لم يُنفذ. قرار تأجيل وظيفة للمرحلة التالية لا يسمح بالقول إن المنتج النهائي اكتمل.

يمكن تحسين التحقق الإنشائي والديناميكي ومحاكاة العملية لاحقًا. في النسخة الأولى لا تدّعِ التحقق من الانحراف أو الاهتزاز أو الاعتمادية الصناعية إذا كان المتاح مجرد حركة كينماتيكية أو فحص أحمال أولي.

## 8. المعمارية الإلزامية: أربع طبقات منفصلة

```text
User / AI Assistant
        ↓
Configuration Engine
        ↓
Engineering Solvers
        ↓
CAD + Simulation + Reports
```

الترتيب أعلاه يوضح مسؤولية كل طبقة، وليس منع إعادة الحساب: CAD يعيد الحجم والكتلة والعطالة والواجهات إلى بيانات الـConfiguration، ثم تُعاد الحسابات عند تغيرها. تبقى نسخة بيانات المشروع المعتمدة هي المرجع المشترك، وليس نص محادثة AI.

| الطبقة | مسؤوليتها | حدودها |
|---|---|---|
| User / AI Assistant | فهم الطلب، اقتراح المواصفات والبدائل، شرح النتائج وطلب استكمال البيانات المؤثرة | لا يخترع عزمًا أو كتلة أو سعرًا أو نجاح فحص؛ لا يتجاوز القيود أو الاعتماد |
| Configuration Engine | تنظيم البارامترات، الوحدات والمجالات، العلاقات بين الأجزاء والأداة، كتالوج المكونات، الإصدارات والقيود | يرفض مدخلات غير صالحة، ويحدد ما يحتاج حسابًا أو تحققًا قبل اعتماد المرشح |
| Engineering Solvers | الكينماتيكا والعزم والسرعة والتشوه والحرارة والتصادم والتحسين وفق النماذج المتاحة | ينتج نتائج عددية مع الافتراضات ومصدر البيانات وحالة الحل وصلاحية النطاق |
| CAD + Simulation + Reports | توليد الهندسة والتجميع، نماذج المحاكاة، STEP وURDF ورسومات وتقارير وBOM وتعليمات التجميع | يستخدم نفس الإصدار ونفس المكونات والنتائج؛ لا يحوّل مرشحًا مرفوضًا إلى ملفات معتمدة |

### عقود البيانات بين الطبقات

أنشئ مخططات بيانات typed وقابلة للتحقق لكل من `ProjectRequirements`, `Workcell`, `RobotConfiguration`, `EndEffector`, `ComponentCatalog`, `InventorySnapshot`, `SolverResult`, `OptimizationRun`, `ApprovalRecord`, `ExportManifest`.

- كل قيمة هندسية لها وحدة ومعنى ونطاق مقبول ومصدر، لا مجرد رقم عائم.
- النتيجة تحمل معرّف التصميم وإصداره وإصدار المحرك والمدخلات التي استخدمها، وطريقة الحساب ومستوى الثقة أو حدود الصلاحية.
- حالة الفحص: `pass / fail / unknown / not_applicable`. لا تُحوّل `unknown` إلى `pass`.
- تحقق من الكتل والأبعاد والتفاوتات، توافق الوحدات، اتساق أطر الإحداثيات، صلاحية مصفوفات العطالة، حدود المكونات، والتوافق بين قيود المهمة.
- قيّم المعيار داخل محرك هندسي أو قواعد صريحة. عبارة AI مثل «هذا مناسب» ليست نتيجة فحص.
- القيم التي تتجاوز المجال أو تفشل القيود تمنع اعتماد المرشح. الأخطاء الفيزيائية غير الظاهرة من مجال القيمة تُكتشف بفحوص متعددة؛ الفصل المعماري لا يضمن اكتشاف كل خطأ تلقائيًا.
- أي حساب طويل له حالة تقدم وإلغاء وحدود زمنية وسبب فشل، مع إبطال النتائج القديمة عند تغير المدخلات.

### أدوات AI Copilot

استخدم واجهات وظائف محددة، مثل:

```text
parse_requirements(request)
validate_requirements(requirements)
query_inventory(filters)
propose_configurations(requirements, catalog, inventory)
evaluate_configuration(configuration, task, workcell)
optimize_configurations(objectives, constraints, bounds)
generate_cad(configuration_revision)
compare_results(configuration_ids)
request_user_approval(configuration_revision)
export_approved_package(approval_id)
```

هذه أسماء عقود مقترحة يجب تنفيذ وظائفها الفعلية؛ لا تجعلها أزرارًا وهمية. لا تمنح نموذج اللغة صلاحية تشغيل أوامر غير مقيدة أو كتابة ملفات التصنيع النهائية مباشرة. يمكنه اقتراح التغيير، لكن الـConfiguration Engine يتحقق منه والمحركات تحسبه.

الاعتماد إجراء صريح من المهندس في الواجهة مرتبط بالإصدار؛ لا يجوز للـAI استدعاء مسار تصدير معتمد عن طريق الادعاء بأن المستخدم وافق.

## 9. AI Copilot وقيود المخزون

مثال لطلب المهندس:

> صمم لي روبوت مدى حركته 1.5 متر وحمولته 10 كجم، مناسب لمناولة صناديق وزنها 6 كجم، واستخدم فقط الموتورات الموجودة في المخزن.

استخرج مواصفات منظمة مبدئيًا مثل:

```json
{
  "robot_axes": 6,
  "application": "box_handling",
  "required_reach": {"value": 1.5, "unit": "m"},
  "stated_payload": {"value": 10, "unit": "kg", "includes_tool": null},
  "workpiece_mass": {"value": 6, "unit": "kg"},
  "motor_selection": {
    "source": "verified_inventory",
    "in_stock_only": true,
    "approved_only": true
  },
  "status": "requires_clarification"
}
```

هنا `null` حالة إدخال مؤقتة متعمدة، وليست بيانات نهائية مقبولة. اسأل هل 10 kg حمولة شاملة للأداة أم للقطعة فقط، واجمع مركز ثقل الصندوق وأبعاده ودورة العمل ونقاط الالتقاط والوضع وغيرها من النواقص المؤثرة. لا تفترض تلقائيًا أن كل الفرق بين 10 و6 كجم متاح للأداة؛ قد توجد محولات وكابلات وهوامش وأحمال إضافية.

المخزون يأتي من مصدر فعلي يحدده المستخدم: ملف Excel/CSV أو اتصال مخزون مصرح به. لا تدّعِ الوصول إلى مخزن Raedbots بمجرد ذكره في الطلب. إذا لم يتوفر المصدر، اطلبه أو بيّن تعذر تطبيق القيد؛ لا تستبدل المخزون بنتائج متجر عام.

لكل سجل مخزون: رقم الصنف والموديل، الكمية المتاحة، حالة الاعتماد، تاريخ التحديث، بيانات الموديل ومصدرها. تحقق أن كميات المحركات المختارة تكفي لعددها في التجميع وأنها متوافقة مع المخفضات والدرايف والطاقة عند انطباق ذلك.

لا تخصم المخزون أو تحجزه أو تطلب شراء تلقائيًا ضمن مهمة التصميم. إن لم تكفِ المكونات أو لا تحقق العزم والسرعة، اعرض عدم وجود حل تحت القيد، مع بديل منفصل يحتاج موافقة المستخدم لتوسيع الكتالوج.

## 10. End Effector كيان قابل للاستبدال

أداة النهاية ليست اسمًا أو شكلًا ثابتًا ملتصقًا بالروبوت. أنشئ كيانًا مستقلًا لها يضم:

| الخاصية | البيانات المطلوبة |
|---|---|
| Mass | كتلة الأداة مع توضيح المرفقات الداخلة في القيمة |
| Center of gravity | إحداثيات مركز الثقل ووحداتها وإطارها المرجعي |
| Inertia | مصفوفة عطالة حول مركز الثقل بوحدة kg·m²، مع تعريف اتجاه المحاور والمصدر |
| TCP | تحويل ثابت من إطار التثبيت إلى نقطة الأداة: موقع واتجاه، مع إمكانية تسجيل عدة TCP عند الحاجة |
| Mounting pattern | أبعاد الفلانشة والثقوب والقلاوظ والتمركز وأي Adapter لازم |
| Cable requirements | عدد الكابلات والخراطيم وأقطارها والحد الأدنى للثني والالتواء وحركة الخدمة |
| Power requirements | الجهد والتيار والقدرة، أو ضغط وتدفق الهواء، ومتطلبات أخرى حسب الأداة |
| Process requirements | قوة القبض أو بيانات العملية ومسار اللحام وسرعته ومسافته وزاويته وغيرها بحسب المهمة |
| Collision geometry | هندسة تصادم مستقلة عن نموذج العرض، وأوضاع الأداة المفتوحة والمغلقة عند الحاجة |

أضف رقم الموديل والإصدار ومصدر البيانات ومعايير القبول. عند غياب بيانات عطالة أو مركز ثقل، يمكن حسابها من CAD وكثافات موثقة أو استخدام تقدير موسوم؛ لا تعتمد نتائج ديناميكية نهائية على أرقام مخترعة.

تبديل الأداة يُحدث الحمل والعطالة وTCP والوصول والتداخل والعزوم والدورة والكابلات والـBOM. الفلانشة الثابتة لا تعني أن كل أداة تركب مباشرة؛ افحص النمط والمحولات والمساحة والكتلة الإضافية.

## 11. الوظائف المتقدمة المطلوبة بعد استقرار الـMVP

هذه متطلبات للمنتج المستهدف، وليست تحسينات اختيارية تُحذف من التسليم. نفّذها تدريجيًا بعد النسخة المحدودة، وحدد للمهندس ما يعمل وما لم يكتمل.

| الوظيفة | التنفيذ المطلوب ومعيار صدق النتيجة |
|---|---|
| Optimization حقيقي | البحث في متغيرات هندسية فعلية ومكونات تجارية، تقييم المرشحين بالمحركات، قيود صريحة وشروط توقف، وPareto Frontier؛ لا تكتفِ بترتيب ثلاثة أمثلة ثابتة |
| أكثر من شكل للوصلة | عدة عائلات أشكال ومقاطع بارامترية صالحة للتصنيع، مثل أنبوب دائري أو مقطع صندوقي أو أجزاء صفائح مجمعة عندما تسمح طريقة التصنيع؛ تحقق من كل قالب ونطاقه |
| Thermal checks | أحمال RMS والذروة ودورة العمل والحرارة المحيطة والتبريد وحدود الموتور والدرايف والمخفض؛ تقدير حراري مناسب قائم على بيانات موثقة، مع بيان ما يحتاج اختبارًا |
| Deflection | تشوه الوصلات والمفاصل والأداة تحت حالات التحميل، وصلابة التوصيلات والمخفضات؛ نموذج مبسط متحقق أولًا ثم FEA عند الحاجة، ومقارنة انحراف TCP بالحد المطلوب |
| Dynamic torque | حساب يعتمد على الكتل والعطالة والجاذبية والتسارع والسرعة والاحتكاك وقوى العملية حسب النموذج المتاح؛ مراعاة كفاءة التخفيض وعطالة المكونات وحدود العزم/السرعة |
| Cable routing | مسار الكابلات والخراطيم وأطوال الخدمة والمثبتات، وفحص الثني والالتواء والتداخل عبر المسار؛ نموذج مسار مبسط لا يُقدَّم كمحاكاة كاملة لسلك مرن |
| Welding path simulation | استيراد أو رسم مسار اللحام، تعريف TCP وزاوية الشعلة ومسافتها وسرعة التقدم، اختبار الاتجاهات والوصول والسرعة والتفرد والتصادم؛ لا تدّعِ محاكاة جودة اللحام الحرارية/المعدنية دون محرك متخصص |
| Gripper payload envelope | حدود حمل مرتبطة بالاتجاه والتسارع ومركز الثقل وفتح الفك وشكل القطعة وقوة القبض والاحتكاك وبيانات الأداة؛ لا تعرض قيمة kg واحدة لكل الحالات |
| Cost and availability | أسعار ومخزون ومصادر وتواريخ وعملات، مع قواعد اعتماد المكونات وكمية الإنتاج والشراء والتصنيع؛ المعلومة القديمة أو المفقودة ظاهرة |
| Manufacturing rules | قواعد حسب العملية: سماكات وأقطار ومقاسات أدوات، عمق الثقوب والقلاوظ وإمكانية الوصول، أنصاف الأقطار والتفاوتات والثني والتثبيت والتجميع؛ القواعد مرتبطة بقدرات الورشة المعروفة |

معادلة الديناميكا العامة المرجعية للمحرّك، مع توثيق اصطلاح إشارات القوى الخارجية ووحدات المفاصل:

```text
tau = M(q) * q_ddot + C(q, q_dot) * q_dot + g(q)
    + friction_terms + external_load_terms
```

ينفذها solver مناسب أو صياغة مكافئة؛ لا يحسبها نموذج اللغة من الوصف. تحويلها إلى متطلبات عمود الموتور يحتاج نسبة التخفيض وكفاءته وعطالاته وشروطه، ولا يختزل دائمًا في قسمة عزم الخرج على النسبة فقط.

افصل درجات التحقق: تقدير أولي / نموذج هندسي متحقق ضمن نطاق / تحليل تفصيلي / اختبار فعلي. النتائج المبسطة مفيدة للمقارنة، لكن لا تُعرض على أنها إثبات تصنيع أو تشغيل صناعي كامل.

## 12. مخرجات CAD والمحاكاة والتقارير

إلى جانب حزمة الملفات السابقة، أضف:

- **URDF + meshes:** روابط ومفاصل ومحاور وحدود وكتل ومراكز ثقل وعطالات وcollision geometry مرتبطة بإصدار التصميم، مع وحدات SI وتحويلات صحيحة من CAD. ملف STEP لا يتحول إلى وصف حركي صحيح دون هذه البيانات.
- **مشهد خلية العمل:** المعدات والعوائق ونقاط المهمة والأداة ومساراتها، بصيغة المشروع، مع ملف محاكاة MJCF عند تنفيذ مسار MuJoCo.
- **تقرير هندسي:** المتطلبات والافتراضات ونتائج كل محور والقيود والدقة المتاحة ومقارنة الـConfigurations وPareto والاختيار المعتمد.
- **تعريف الأداة:** بيانات End Effector وTCP وواجهاتها وإصدارها ضمن المشروع.
- **سجل تحقق وتصدير:** ما تم حسابه وفحصه وما بقي مجهولًا، وربط الملفات بإصدار الاعتماد وتاريخ مصادر المخزون والأسعار.

تحقق بتحميل URDF في قارئ مستقل أو أداة المحاكاة المناسبة، ومقارنة الحركة الأمامية وأطر المفاصل وTCP مع المحرك الهندسي لنفس الوضعيات. لا تكتفِ بصحة XML. تحقق أن النماذج التصادمية تحتفظ بالحيز المهم رغم التبسيط.

## 13. تنفيذ مبسّط داخليًا

- استخدم CadQuery للنمذجة البارامترية وRobotics Toolbox للحركة وOCP CAD Viewer أثناء التطوير.
- استخدم Three.js لعرض التطبيق المستقل. ليس مطلوبًا أن يثبّت المستخدم VS Code كي يستخدم البرنامج النهائي.
- احتفظ بـBuild123d كبديل تطوير؛ لا تجعل وجوده شرطًا إضافيًا لاستخدام المنتج.
- MuJoCo تطوير لاحق؛ لا تؤخر مخرجات CAD والمشتريات والتصنيع والرسومات والـBOM بسبب إضافة محاكاة متقدمة.
- يلزم تنفيذ طبقة رسومات هندسية فعلية لإنتاج المساقط والأبعاد والعناوين. تثبيت CadQuery وحده لا ينتج تلقائيًا رسومات تصنيع مكتملة أو تعليمات تجميع.
- أبقِ البرنامج لمستخدم واحد، بلا تسجيل حسابات أو إدارة فرق أو صفحات إعداد معقدة في البداية.
- لا تبدأ بتطبيق كامل لتصميم موتور أو جيربوكس من الداخل؛ استخدم المكونات القياسية المشتراة وصمّم واجهات تركيبها.

## 14. اختبارات القبول المرحلية

بعد تأسيس القاعدة المرجعية واختبارها، سلّم النسخة الأولى بالنطاق المحدد أعلاه، ثم أكمل الرسومات وتعليمات التجميع وبقية حزمة المنتج. اختبارات القبول التالية تُطبّق على الوظائف الموجودة في المرحلة المعنية؛ لا تعتبر نجاح الـMVP اعتمادًا لاكتمال كل المنتج. لا تعتبر واجهة بها أزرار تصدير غير عاملة نسخة مكتملة.

يجب التحقق من:

1. وجود أجزاء صلبة منفصلة وتجميع صحيح لروبوت 6 محاور، مع قراءة ملفات STEP المصدّرة مجددًا.
2. تطابق أرقام الأجزاء وإصداراتها وكمياتها بين التجميع والرسومات والقوائم وتعليمات التجميع.
3. وجود كل جزء مصنّع في قائمة التصنيع وربطه بملف CAD ورسم 2D؛ وأي نقص ظاهر في حالة المخرجات.
4. وجود كل جزء مشترى في قائمة المشتريات مع الموديل ومصدره أو حالة «لم يتم الاختيار».
5. مطابقة حركة العرض لتعريف المحاور وحدودها، وإظهار التداخلات المكتشفة.
6. عدم الاكتفاء بصورة ثابتة بدل رسم هندسي؛ افتح ملفات 2D وتحقق من وضوح الأبعاد وعدم تداخلها.
7. تنفيذ تغيير في طول ذراع وتحديث CAD والرسومات والكتل المتأثرة والبيانات التابعة له، مع إعادة تقييم صلاحية المكونات المشتراة.
8. إمكانية فتح الحزمة المصدّرة ومعرفة المطلوب شراؤه والمطلوب تصنيعه وطريقة التجميع دون الرجوع للمحادثة.

اختبارات قبول إضافية إلزامية:

9. توثيق تحليل كادات فعلية وإعادة بناء مرجع واختبار تغيير أبعاده قبل اعتماد القوالب الداخلية؛ لا يكفي ذكر أسماء روبوتات.
10. تشغيل التطبيق من مشروع نظيف دون الاعتماد على ملفات بحث مؤقتة أو مطالبة المستخدم بإعادة مرحلة البحث.
11. التمييز في ROM بين نقطة قابلة للوصول بموقعها وأخرى يفشل اتجاه أداتها، ونقطة أو مسار يصطدم بعائق، مع عرض الأسباب الصحيحة.
12. تغيير موضع قاعدة الروبوت وإعادة تقييم نقاط المهمة دون الخلط بين الإحداثيات العالمية والمحلية.
13. تعديل أبعاد الروبوت وتبديل مقاس مكون قياسي والتحقق من الواجهات، مع تحديث النتائج والملفات التابعة.
14. اختبار هدف تحسين مع قيود مثبتة، وعرض فشل صريح عند عدم وجود حل بدل إخراج نتيجة غير مستوفية.
15. منع إصدار الحزمة النهائية قبل الاعتماد؛ وإلغاء صلاحية الاعتماد عند تعديل بيانات مؤثرة، مع الاحتفاظ بالإصدار السابق.
16. وجود المدخلات الاثني عشر التي طلبها المستخدم ومتغيرات الاختيار الاثني عشر للنظام، مع وحدات وحالات تثبيت وحدود واضحة.
17. احترام خامة أو أداة أو موتور ثابت أثناء التحسين، وعدم تبديله دون تغيير صريح من المستخدم؛ وإظهار عدم إمكان الحل عند تعارضه مع القيود.
18. إعادة حساب كتلة الروبوت وأحمال المحاور وتكلفته عند تغيير موتور أو جيربوكس أو أداة، مع منع اعتماد نتائج من دورة حساب سابقة.
19. فصل دقة الحركة عن التكرارية، والتكلفة المعروفة عن الناقصة، وعزم الموتور عن عزم خرج التخفيض في المدخلات والنتائج.
20. التحقق من أن الأداتين تختبران كحالات تحميل ومسارات مستقلة، وأن التصميم المشترك يستوفي أسوأ متطلبات كل محور عبر جميع الحالات، لا وزن الأداة الأثقل فقط.
21. حساب Pareto Frontier من مرشحين متسقي الأهداف والوحدات؛ استبعاد مرشح مخالف لحمولة إلزامية أو مسار مطلوب وإظهار سبب الاستبعاد.
22. احترام نطاق الـMVP: 6 محاور، 2–3 أحجام وصلات، 3 موديلات محركات، 3 مخفضات، أداتان محددتان، فلانشة ثابتة، خامتان وطريقة أو طريقتا تصنيع.
23. اختبار تغيير أوزان الترتيب دون تغيير نتائج الحسابات الأصلية أو إخفاء جبهة البدائل، وحفظ اختيار المهندس مع إصدار التصميم.
24. إرسال قيمة سالبة أو وحدة خاطئة أو موتور خارج المخزون من Copilot والتحقق من رفضها أو طلب تصحيحها دون توليد حزمة معتمدة.
25. التحقق من أن نتائج AI المعروضة تربط إلى نتيجة solver فعلية لنفس الإصدار، وأن غياب نتيجة حساب لا يتحول إلى ادعاء نجاح.
26. تبديل Gripper بالشعلة والتحقق من تغير TCP والكتلة ومركز الثقل والعطالة والتداخل والمسار والـBOM بحسب بيانات كل أداة.
27. تحميل URDF والتحقق من المحاور وحدود الحركة والوحدات وTCP ومقارنة نتائجه مع تعريف الروبوت الأصلي.
28. اختبار التحسين على أكثر من شكل وصلة، وفحص العزم الديناميكي والحرارة والتشوه والكابلات والعملية وقواعد التصنيع عند اكتمال محركاتها، مع تمييز أي قيد غير متحقق.
29. عند قيد «الموتورات الموجودة في المخزن فقط»، لا يُقبل موديل غير موجود أو كمية غير كافية أو سجل غير موثق على أنه متاح.
30. تجهيز أداة STEP Parts من الحزمة المرفقة والتحقق من النسخ، واستخدام اختيار بمعرّف مؤكد بعد مطابقة المواصفات بدل تنزيل أول نتيجة بحث تلقائيًا.
31. تجربة CAD لموتور ومسمار ومحمل من المكونات المختارة فعليًا، والتحقق من STEP والأبعاد والبصمة عندما تتوفر؛ تسجيل الشبكة المعطلة بصورة مختلفة عن «لا توجد نتيجة».
32. تمييز رابط تنزيل CAD عن رابط المورد، والتحقق من أن تقرير الشراء يشير لنفس الموديل والمقاس والكمية في BOM.
33. إعادة توليد تقرير الشراء وسجل CAD عند تغيير مكون أثناء التحسين، وإظهار CAD المفقود والمصادر غير المتحققة بدل اختلاقها.
34. التحقق من أن العناصر غير الهندسية مثل اللاصق لا تدخل في مقام نسبة تغطية CAD، وأن المكونات المهمة المفقودة تظهر رغم وجود مسامير كثيرة.
35. إعطاء الأولوية لمصادر شراء فعلية داخل مصر، وعرض EGP والمدينة والتواصل المنشور، وتمييز المخزون المحلي عن التوريد بالاستيراد والمورد الخارجي دون الادعاء بتوفر غير موثق.
36. إعادة تشغيل حساب من manifest محفوظ ومقارنة النتائج ضمن سماحيات موثقة، مع منع إعادة استخدام Cache بعد تغيير إصدار محرك أو بيانات مؤثرة.
37. وصول نتيجة مهمة قديمة بعد تعديل التصميم لا يغير نتائج الإصدار الجديد أو اعتماده.
38. اختبار استعادة مشروع وملفاته من النسخة الاحتياطية، والتحقق من اتساق أرقام الأجزاء وروابطها وإصداراتها.
39. تمييز اعتماد حزمة للمراجعة أو النموذج التجريبي عن اعتماد التصنيع، ومنع نموذج اللغة من ترقية الحالة بنفسه.

المخرج المطلوب أداة هندسية بسيطة في الاستخدام. اكتمال ملفات المشروع لا يساوي اعتماد الروبوت للتصنيع أو التشغيل؛ حالات المراجعة تظهر باختصار بجوار المخرجات المعنية.


## 15. خطة تنفيذ قابلة للقياس وسجل تحقق

دمج هذا القسم تحسينات التنفيذ من وثيقة «منصة رائد بوتس لتصميم وتحسين روبوتات 6 محاور.md»، مع الحفاظ على نطاق المستخدم: STEP Parts، تحليل CAD الحقيقي، خلية العمل وROM، التوريد المصري، الاعتماد، رسومات 2D وتعليمات التجميع. لا يحل هذا القسم محل المتطلبات السابقة ولا يوسّع واجهة المستخدم بلا حاجة.

### 15.1 تسلسل التنفيذ ومسؤولية كل مرحلة

الأدوار التالية مسؤوليات يمكن أن يجمعها شخص واحد، وليست اشتراطًا لتوظيف فريق كامل. عيّن مسؤولًا هندسيًا عن قبول النتائج. المهندس يراجع القرار، والوكيل ينفذ العمل المصرح به ولا يتوقف لطلب موافقة على كل ملف أو اختبار.

| المرحلة | ما يُنفّذ | دليل الانتهاء |
|---|---|---|
| 0 — قاعدة هندسية | بحث الشركة والكادات والمكونات، تحليلها، قوالب الروبوت والأداتين وحدود التشغيل وطرق التصنيع | مصادر وترخيص وفحوص CAD، كتالوج محدود، وحالات مستقلة ذات نتائج مرجعية |
| 1 — البيانات | مخططات المتطلبات والمكونات والأداة والوحدات والإصدارات وقواعد القبول | رفض بيانات ناقصة مؤثرة، حفظ وإعادة تحميل مشروع دون تغيير معناه |
| 2 — الحركة والأحمال | FK وIK وTCP وحدود المفاصل، جاذبية وأحمال وسرعة، وتعريف حالات المهمة | مقارنة بحالات مرجعية؛ التحليل الساكن وحده لا يثبت صلاحية الديناميكا أو زمن الدورة |
| 3 — CAD والواجهات | أجزاء بارامترية وتجميع وواجهات المكونات والأداة وSTEP وGLB | ملفات تُفتح مستقلًا، أبعاد وواجهات صحيحة، وتغيير بارامتر يعيد بناء الأجزاء المتأثرة |
| 4 — تجربة المستخدم | خلية العمل وROM واختيار الأداة ونقاط المهمة والتعديل والإصدارات | تجربة تصميم وتعديل والتحقق من الوصول والتصادم ونتائج تتطابق مع الإصدار المعروض |
| 5 — البدائل والتحسين | توليد مرشحين محدودين، تشغيل المحركات، سجل الرفض، Ranking وPareto | لا يدخل مرشح مخالف القيود ضمن الحلول الصالحة، وإمكان إعادة البحث والتحقق منه |

### 15.2 أول دورة تنفيذ عملية

بعد تثبيت قاعدة مرجعية أولية من المرحلة 0:

1. أنشئ مشروعًا واحدًا ومخططات الروبوت والأداة والموتور والمخفض والوحدات.
2. أدخل نموذج 6 محاور موثقًا وGripper وشعلة ببيانات حقيقية أو تقديرات مصرح بها وموصوفة.
3. نفّذ FK وTCP واختبارات الجاذبية الأولية، وقارن بحالات مستقلة معروفة.
4. أضف نقطة API للحساب وواجهة صغيرة لتغيير الأداة وعرض النتيجة.
5. احفظ المدخلات والنتائج وإصدارات المصدر لتستطيع إعادة نفس التجربة.

قِس زمن التشغيل على جهاز معروف وسجّله. لا تعد بزمن أقل من دقيقة أو أي حد ثابت دون قياس حجم الحالة والهندسة وعدد المرشحين. النتيجة المقبولة لهذه الدورة هي حساب أولي قابل للتتبع، ثم يُستكمل CAD والتحسين والمخرجات.

### 15.3 بنية برمجية خفيفة مع قابلية التوسع

ابدأ بتطبيق واحد مقسّم إلى وحدات واضحة: `domain`, `catalog`, `engineering`, `cad`, `optimization`, `procurement`, `reports`, `api`, `web`, `tests`. خزن الأصول والبيانات المرجعية وقواعد التصنيع باصدارات. لا يلزم تحويل كل وحدة إلى خدمة منفصلة.

- احتفظ بـCadQuery كمحرك CAD الأساسي وفق الخطة الحالية؛ لا تغيّر المحرك لمجرد أن الوثيقة المقارنة رشحت Build123d. اختيار محرك آخر يحتاج سببًا عمليًا وتجربة توافق للمخرجات.
- يمكن استخدام FastAPI وطبقة تحقق مثل Pydantic للـAPI. ثبّت نسخًا متوافقة ومختبرة، لا مجرد «أحدث إصدار».
- لمستخدم واحد يمكن بدء التخزين بقاعدة محلية مناسبة وملفات منظمة، مع واجهة تخزين تسمح بالنقل لاحقًا. PostgreSQL وRedis وCelery ليست شروطًا لبدء العمل؛ أضفها حين تبررها مشاركة المستخدمين أو حجم الوظائف أو متطلبات النشر.
- شغّل CAD والتحسين الطويل في عامل منفصل عن طلب الواجهة، مع تخزين حالة المهمة. لا توقف التفاعل أثناء الحساب.
- ROS 2 وMoveIt 2 وPinocchio خيارات تكامل لاحقة عند وجود حاجة فعلية لتخطيط أكثر تقدمًا أو تكامل متحكمات أو محرك ديناميكا بديل. لا تفرضها كلها قبل عمل النموذج وURDF والمحركات الأساسية.
- لا تضف نظام أدوار وشاشات حسابات معقدًا للنسخة المحلية لمستخدم واحد. إذا نُشر التطبيق لمستخدمين متعددين، طبّق حدود المشروع وصلاحيات القراءة والتعديل والاعتماد على مستوى الخادم.

استخدم Cache فقط إذا تطابقت بيانات التكوين والمهمة والبيئة والمكونات وقواعد التصميم وإصدارات المحركات ذات الصلة. تغيّر مصدر أو إصدار مؤثر يُبطل النتائج التابعة له. احفظ المرشحين المرفوضين وأسبابهم مع الحدود التي فشلت، لا الناجحين فقط؛ يمكن حفظ بياناتهم الحسابية دون ملفات CAD كاملة لتقليل الحجم.

### 15.5 سجل إعادة الإنتاج

لكل حساب وتحسين وتصدير احفظ:

- متطلبات المشروع والتكوين والخلية والمسار والأداة والمكونات بإصداراتها وبصماتها.
- الكود المولّد أو قالب CAD وإصدار قواعد التصميم ومعرّف Git commit أو build.
- إصدارات المحركات والحزم ونظام التشغيل المؤثر وملفات تثبيت الاعتماديات.
- إعدادات الحل والحدود العددية ونقاط الاختبار وخطوة أخذ العينات وseed العشوائي إن استُخدم.
- النتائج والوحدات وحالة كل فحص ومصدر البيانات، والمرشحين وسبب القبول أو الرفض.
- ملفات STEP وGLB وURDF وBOM والرسومات والتقارير مع manifest وبصمة لكل ملف.
- قرار المراجع والإصدار الذي راجعه وتاريخ القرار وحزمة التصدير التابعة له.

الهدف إعادة إنتاج النتائج ضمن سماحيات محددة، لا اشتراط تطابق بايتات STEP أو الصور إذا احتوت طوابع زمنية أو تغيّرت طريقة التسلسل. افحص الشكل والأبعاد والخواص والقيم ذات المعنى. اعتمد بصمة الملف لتتبع الملف نفسه، وفحوصًا هندسية للتحقق من التكافؤ.

### 15.6 حالات التصميم والمراجعة

افصل بين موافقة المستخدم على اختيار التصميم، ومراجعة صلاحيته لنموذج تجريبي، واعتماده للتصنيع. حالات التصميم المقترحة:

| الحالة | معناها |
|---|---|
| DRAFT | إدخال أو تعديل لم تكتمل حساباته |
| CALCULATED | اكتمل تشغيل الحساب؛ لا يعني تلقائيًا نجاح كل القيود |
| ENGINEERING_REVIEW | إصدار ثابت معروض للمراجعة ومرفق به حالات الفحوص |
| APPROVED_FOR_PROTOTYPE | قبول موثق لغرض النموذج التجريبي ضمن قيود معلنة |
| APPROVED_FOR_MANUFACTURING | مراجعة موثقة لغرض التصنيع بعد تحقق متطلبات هذا النطاق |
| REJECTED | رفض مع أسباب قابلة للمراجعة |

يمكن للمستخدم اعتماد اختيار التصميم وإصدار حزمة موسومة «للمراجعة» أو «للنموذج التجريبي» وفق حالة الأدلة. لا تُسمَّ حزمة غير مكتملة التحقق «معتمدة للتصنيع». نقص دليل متعلق بقيد إلزامي يمنع الانتقال إلى الحالة التي تتطلبه، دون منع تحليل المرشح أو عرض معاينته.

قرار موافقة المستخدم في الواجهة لا يُلغى بطلب تأكيد مكرر لنفس الإصدار والغرض. أي تغيير هندسي مؤثر ينشئ DRAFT جديدًا ويُبقي القرار السابق وملفاته محفوظة. اجعل حالات المكوّن واعتماده مستقلة عن حالة التصميم. الـAI لا يعتمد مكوّنًا أو ينتحل هوية المراجع.

### 15.7 اختبارات مرجعية مستقلة وتصحيح قواعد الاختبار

أنشئ حالات Golden ذات مصدر مستقل: معادلة يدوية لحالة بسيطة، نموذج موثّق، محرك مستقل مناسب، أو قياس فعلي. مخرجات نفس الكود تحت الاختبار ليست وحدها مرجعًا لإثبات صحته. عرّف tolerance مطلقًا ونسبيًا مناسبًا لكل وحدة، وسجّل سبب تغييره.

حالات لازمة: روبوت بلا أداة، جريبر مع قطعة، شعلة مع TCP مختلف، ذراع ممدود، حمل زائد، تعارض فلانشة، نقطة خارج الوصول، وضعية قريبة من التفرد، اصطدام بعائق، وموتور غير متاح في المخزون.

لا تنقل الاختبارات الفيزيائية العامة التالية دون شروط:

- «زيادة كتلة الأداة لا تقلل العزم المطلوب» ليست قاعدة مطلقة لكل محور ووضعية: يمكن أن تتعاكس مساهمة الأداة مع وزن موازن أو حمل آخر. اختبر الاتجاه والمقدار المتوقعين في حالة معروفة محددة، أو تحقق من تغير مساهمة الجاذبية وفق ذراع العزم والتحويلات الثابتة.
- «تقليل طول وصلة لا يزيد العزم» ليس invariant عامًا إذا تغيرت وضعية الحل أو توزيع الكتل أو ذراع العزم للمحاور الأخرى. استخدم نموذجًا تحليليًا بشروط محددة.
- تبديل الأداة مع **جسم روبوت مقفول** يغير الأداة والمحولات والحسابات دون تعديل الجسم؛ أما **إعادة تحسين الجسم للأداة** فيجوز أن تغيّر الروبوت. اختبر النمطين ولا تخلطهما.

اختبارات مناسبة: FK/IK round-trip على الوضعية لا على تطابق الزوايا فقط، حفظ الوحدات والتحويلات، TCP من تركيب التحويلات، تناظر واتساق العطالة، رفض مكوّن خارج القيود، منع تصدير إصدار غير مطابق للاعتماد، وإعادة بناء CAD بعد تغيير واجهة فعلية.

### 15.8 دقة عقود الأداة والنتائج

عند تحويل أمثلة الـDomain Model إلى كود حقيقي:

- TCP يحتاج موقعًا **واتجاهًا** وإطارًا مرجعيًا. ثلاث قيم للموقع وحدها لا تكفي؛ استخدم Pose بتحويل متجانس أو موقع وquaternion مع اصطلاح معلوم.
- العطالة ليست ثلاث قيم بلا تفسير. استخدم tensor متماثل 3×3 أو مركباته الست المستقلة، حول نقطة وفي إطار محددين. القيم الرئيسية الثلاث تكفي فقط مع إطار محاورها الرئيسية وتحويله الموثق. تحقق من القيم الرئيسية وعدم سلبية الطاقة والاتساق الفيزيائي.
- الخامات وطرق التصنيع لكل جزء أو مجموعة، وليس `material_id` واحدًا يفرض خامة على كل الروبوت.
- نتائج العزم والسرعة ترتبط بالمحور وحالة التحميل والزمن أو الذروة والوحدة وجانب الموتور/الخرج، ولا تكتفي بقائمة ست قيم بلا معنى.
- `valid` أو `collision_free` وحدهما لا يميزان الفشل عن عدم إجراء الاختبار. احتفظ بحالة كل فحص ومجاله وطريقته وأسباب الرفض، ثم اشتق ملخص الصلاحية.

### 15.9 معايرة النموذج التجريبي وحماية المشروع

في Pilot فعلي، قارن أبعاد الأجزاء وكتلتها وواجهاتها، الخلوص والتكرارية والتشوه تحت حمل معلوم والتيار والحرارة وزمن الدورة بحسب المتاح. قياس التيار ليس قياس عزم مباشرًا دون ثابت موتور ونموذج ودقة معلومة. سجّل ظروف القياس ومعايرة الأجهزة وعدم اليقين والفروق عن المحاكاة.

أنشئ `CalibrationRecord` يحدد القياسات وإصدار النموذج وتعديل المعاملات ودليل تحسن التنبؤ. لا تغيّر معاملًا خفية حتى يطابق نتيجة اختبار واحدة؛ استخدم حالات أخرى للتحقق من أن المعايرة تحسّن التعميم داخل النطاق. لا تبدأ تشغيل حركة فعلية تلقائيًا من طلب Copilot.

احفظ الأصول ونسخها وسجل التغييرات في مساحة خاصة بالمشروع مع نسخ احتياطي واختبار استعادة. للطلبات الخارجية إلى خدمات AI أو مصادر الأجزاء، أرسل فقط ما يلزم مثل مواصفات أو رقم موديل، ولا ترفع CAD الشركة الكامل تلقائيًا. احتفظ بالمصادر والتراخيص ونتائج الاختبار، وطبّق صلاحيات إضافية عند الانتقال إلى نشر متعدد المستخدمين.

### 15.10 معيار اكتمال كل إصدار

وجود واجهة جذابة أو تقرير طويل لا يكفي. اربط كل متطلب بحالة: منفذ ومختبر / منفذ غير متحقق / مؤجل لمرحلة محددة / متعذر بسبب موثق. أرفق دليل اختبار أو ملف ناتج عند الادعاء باكتمال وظيفة. لا تحذف المتطلبات النهائية المؤجلة من قائمة التسليم.

````markdown
# STEP Parts

Provenance: maintained in [earthtojake/text-to-cad](https://github.com/earthtojake/text-to-cad).
Use the installed local skill files as the runtime source of truth; the
repository link is only for provenance and release review.

## Overview

Use the hosted step.parts machine endpoints instead of scraping HTML or relying on local repository files. Treat `https://api.step.parts` as the canonical API origin and `https://www.step.parts` as the site/static-asset origin unless the user provides a different hosted mirror. Network/DNS failures are inconclusive: if `api.step.parts` cannot be reached from the sandbox, retry once with network permission before reporting a miss or using placeholder geometry. Do not describe a part as unavailable unless the API was reachable and returned no relevant candidates.

When a CAD assembly includes named off-the-shelf actuators, servos, motors, electronics boards, connectors, or other purchasable components, search step.parts before creating simplified placeholder geometry. For named servos, motors, and actuators, search both exact model strings and common aliases/vendor spellings before giving up. For example, `STS3215` may also appear as `ST3215`, `3215`, `Waveshare Feetech ST3215`, or under `family=feetech`. If the API was reachable and no exact or near-exact match is available, record the search miss and then use a documented envelope or simplified stand-in.

## Quick Workflow

1. Interpret the requested part into search terms and optional facets:
   - `q` for fuzzy tokens, standards, aliases, dimensions, source/product URLs, and attribute names/values.
   - `category`, `family`, `standard`, or `tag` when the user gives an exact facet.
2. Search `/v1/parts` and inspect `items`, `total`, and `facets`. For actuator model numbers, retry likely aliases, dropped letters, vendor names, and relevant family facets before treating an empty result as a miss.
3. If results are ambiguous, present the best few options with `id`, `name`, `standard`, and key attributes before choosing. If one result clearly matches, return the selected record details without downloading unless the user asked for a local STEP file.
4. When an exact or near-exact off-the-shelf actuator model is found, prefer downloading and using its STEP file unless there is a clear assembly-time reason to use a simplified envelope. Record that choice explicitly.
5. When the user asks to download or save a STEP file, download its `stepUrl`, then verify the file with the record's `sha256` when present.
6. Return the local path when downloaded, plus the selected part id and page/API URLs so the user can trace provenance.

## CAD Viewer Handoff

After completing step.parts work that creates or updates a local `.step` or `.stp` file, you must ALWAYS hand the explicit file path to `$cad-viewer` when that skill is installed. `$cad-viewer` must start CAD Viewer if it is not already running and return link(s) to the relevant created or updated file(s); if `$cad-viewer` is unavailable or startup fails, report that instead of silently omitting the handoff.

```

Useful options:

- `--origin`: override `https://api.step.parts` only when the user provides another hosted API origin.
- `--tag`, `--category`, `--family`, `--standard`: repeatable facet filters.
- `--out-dir`: destination directory for downloads. It defaults to the system temp directory, so pass it whenever the file should survive in the project.
- `--filename`: rename the one downloaded file; rejected together with `--all`.
- `--limit`, `--page`: search page size (default 10, API cap 500) and 1-based page.
- `--all`: with `--download`, download every result on the returned page as individual STEP downloads.
- `--overwrite`: replace an existing output file. Without it, an existing destination is refused rather than overwritten.

The script prints JSON to stdout. For searches, it prints matched records. For downloads, it prints saved file paths, checksums, and source URLs. Failures print a one-line plain-text message to stderr and exit 1.

## API Reference

Read `references/step-parts-api.md` when you need endpoint details, field meanings, or query semantics. Prefer:

- `/v1/parts` for filtered search with absolute asset URLs.
- `/v1/parts/{id}` for one enriched record.
- Returned `stepUrl` for STEP downloads.
- `/v1/catalog/parts.index.json` for a compact discovery index.
- `/v1/catalog/schema` for field and family attribute meanings.
- `/v1/openapi.json` when generating a client or tool.

## Search Guidance

- Query tokens are ANDed by the API, so start specific but not overconstrained. For example, use `M3 SHCS 12` before adding exact family and standard filters.
- Values within one facet are ORed together, and selected `tag`, `category`, `family`, and `standard` fields are ANDed together. Use exact facets to narrow within known categories, then rank manually by name and attributes.
- Standards can be queried as `ISO 4762`, `ISO4762`, or the exact `standard.designation`.
- The `attributes` object contains family-specific facts such as `thread`, `lengthMm`, `bore1Mm`, `material`, `profileSeries`, `slotSizeMm`, and dimensions in millimeters.
- Part, GLB, and PNG URL patterns are predictable on `https://www.step.parts`; STEP URLs are environment-aware and may resolve to GitHub LFS media in production. Use catalog/API `stepUrl` for downloads.
````

````markdown
# step.parts API Reference

## Origins

Default to the API origin `https://api.step.parts`. Use a different origin only when the user supplies another hosted step.parts-compatible API domain. Static HTML pages live on `https://www.step.parts`; GLB and PNG preview URLs in API records point directly at Vercel Blob. STEP URLs are environment-aware and production records use commit-pinned GitHub LFS media. If the API domain does not resolve, treat the hosted service as unavailable and ask for a deployed origin when a live download is required.

## Machine Endpoints

| Endpoint | Use |
| --- | --- |
| `https://www.step.parts/llms.txt` | Human-readable agent guide with endpoint summary and examples. |
| `/v1/parts` | Search, filter, paginate, and retrieve absolute asset URLs. |
| `/v1/parts/{id}` | Fetch one enriched part record by stable id. |
| `/v1/catalog/schema` | JSON Schema, field semantics, result ordering, and family attribute meanings. |
| `/v1/catalog/parts.index.json` | Compact id/name/facet discovery index for cheap lookups before fetching details. |
| `/v1/openapi.json` | OpenAPI 3.1 contract for generating clients/tools. |

## `/v1/parts` Query Parameters

- `q`: tokenized metadata search across id, name, description, category, family, stepSource, productPage, tags, aliases, standard fields, attribute keys, and attribute values. Every token must match.
- `tag`, `category`, `family`, `standard`: repeatable filters. Values may also be comma-separated. Values within one facet are ORed, and selected facet fields are ANDed together.
- `page`: 1-based page number.
- `pageSize`: default `100`, max `500`.

Unfiltered results start with a fixed 100-part showcase, then continue in stable source catalog order. Filtered results are ordered by stable source catalog order.

Examples:

```text
https://api.step.parts/v1/parts?q=M3&tag=screw&page=2
https://api.step.parts/v1/parts?pageSize=100
https://api.step.parts/v1/parts?category=fastener&family=socket-head-cap-screw&standard=ISO%204762
https://api.step.parts/v1/parts?q=lengthMm%2012
```

## Response Fields

`/v1/parts` returns:

- `catalog`: part count, last modified timestamp, catalog checksum, and URLs for schema/OpenAPI.
- `items`: enriched part records with absolute `pageUrl`, `apiUrl`, `stepUrl`, `glbUrl`, and `pngUrl`.
- `page`, `pageSize`, `total`, `totalPages`, `hasNextPage`, `hasPreviousPage`.
- `facets`: available `tags`, `categories`, `families`, and `standards` with counts.
- `filters`: parsed active filters.

Each part record contains:

- `id`: stable snake_case identifier and asset filename base.
- `name`, `description`, `category`, `family`, `tags`, `aliases`.
- `standard`: optional `{ body, number, designation }`.
- `attributes`: family-specific scalar facts.
- `stepUrl`, `glbUrl`, `pngUrl`.
- `byteSize`, `sha256`.

## Asset URL Patterns

Use returned URLs when possible. Patterns are:

```text
https://www.step.parts/step/{id}.step
https://www.step.parts/parts/{id}
```

Preview assets have no predictable pattern: use the absolute `glbUrl` and `pngUrl` returned by the API record. They are served from Vercel Blob.

The `/step/{id}.step` route serves local checked-out STEP bytes in local/dev mode and redirects to commit-pinned GitHub LFS media in production.

## Download And Verification

When downloading a STEP file:

1. Fetch a part record from `/v1/parts` or `/v1/parts/{id}`.
2. Download `stepUrl`.
3. Compare the file SHA-256 to the part record's `sha256` when it is not null.
4. Keep the original `.step` extension and preserve the source id in the filename unless the user asks otherwise.
````

````python
#!/usr/bin/env python3
"""Search step.parts for common standard parts and download STEP files."""

from __future__ import annotations

import argparse
import hashlib
import json
import sys
import tempfile
import urllib.error
import urllib.parse
import urllib.request
from pathlib import Path
from typing import Any


DEFAULT_ORIGIN = "https://api.step.parts"
DEFAULT_OUT_DIR = tempfile.gettempdir()
USER_AGENT = "step-parts-skill/1.0"


def parse_args() -> argparse.Namespace:
    parser = argparse.ArgumentParser(
        description=(
            "Search the step.parts hosted catalog for low-level common standard parts "
            "(screws, bolts, bearings, electronics parts, motors, connectors, etc.) "
            "and optionally download canonical STEP files."
        ),
    )
    parser.add_argument("query", nargs="?", help="Fuzzy search query, for example 'M3 socket head 12'.")
    parser.add_argument("--id", dest="part_id", help="Fetch a specific part id instead of searching.")
    parser.add_argument("--origin", default=DEFAULT_ORIGIN, help=f"API origin. Default: {DEFAULT_ORIGIN}")
    parser.add_argument("--download", action="store_true", help="Download the selected STEP file.")
    parser.add_argument("--all", action="store_true", help="With --download, download every result on the returned page.")
    parser.add_argument("--out-dir", default=DEFAULT_OUT_DIR, help="Directory for downloaded STEP files. Default: active temp directory.")
    parser.add_argument("--filename", help="Filename to use when downloading one selected part.")
    parser.add_argument("--overwrite", action="store_true", help="Overwrite an existing downloaded file.")
    parser.add_argument("--limit", type=int, default=10, help="Search page size. The API caps this at 500.")
    parser.add_argument("--page", type=int, default=1, help="1-based search page.")
    parser.add_argument("--tag", action="append", default=[], help="Repeatable tag filter.")
    parser.add_argument("--category", action="append", default=[], help="Repeatable category filter.")
    parser.add_argument("--family", action="append", default=[], help="Repeatable family filter.")
    parser.add_argument("--standard", action="append", default=[], help="Repeatable standard filter, for example 'ISO 4762'.")
    parser.add_argument("--timeout", type=float, default=30.0, help="HTTP timeout in seconds.")
    return parser.parse_args()


def origin_url(origin: str) -> str:
    parsed = urllib.parse.urlparse(origin)
    if not parsed.scheme or not parsed.netloc:
        raise SystemExit(f"Invalid origin: {origin!r}")
    return origin.rstrip("/")


def build_url(origin: str, path: str, params: list[tuple[str, str]] | None = None) -> str:
    url = f"{origin_url(origin)}{path}"
    if params:
        return f"{url}?{urllib.parse.urlencode(params)}"
    return url


def request(url: str, timeout: float) -> bytes:
    req = urllib.request.Request(url, headers={"User-Agent": USER_AGENT})
    try:
        with urllib.request.urlopen(req, timeout=timeout) as response:
            return response.read()
    except urllib.error.HTTPError as exc:
        detail = exc.read().decode("utf-8", errors="replace")
        raise SystemExit(f"HTTP {exc.code} for {url}: {detail}") from exc
    except urllib.error.URLError as exc:
        raise SystemExit(f"Failed to fetch {url}: {exc.reason}") from exc


def fetch_json(url: str, timeout: float) -> Any:
    data = request(url, timeout)
    try:
        return json.loads(data)
    except json.JSONDecodeError as exc:
        raise SystemExit(f"Expected JSON from {url}: {exc}") from exc


def search_parts(args: argparse.Namespace) -> dict[str, Any]:
    params: list[tuple[str, str]] = [
        ("page", str(max(1, args.page))),
        ("pageSize", str(max(1, args.limit))),
    ]
    if args.query:
        params.append(("q", args.query))
    for key in ("tag", "category", "family", "standard"):
        for value in getattr(args, key):
            params.append((key, value))
    return fetch_json(build_url(args.origin, "/v1/parts", params), args.timeout)


def get_part(args: argparse.Namespace, part_id: str) -> dict[str, Any]:
    safe_id = urllib.parse.quote(part_id, safe="")
    return fetch_json(build_url(args.origin, f"/v1/parts/{safe_id}"), args.timeout)


def selected_parts(args: argparse.Namespace) -> list[dict[str, Any]]:
    if args.part_id:
        return [get_part(args, args.part_id)]

    result = search_parts(args)
    items = result.get("items", [])
    if not items:
        raise SystemExit("No parts matched the query.")
    if args.download and args.all:
        return items
    return [items[0]]


def filename_for(part: dict[str, Any], requested_filename: str | None, allow_requested: bool) -> str:
    if requested_filename and allow_requested:
        return requested_filename
    step_url = str(part.get("stepUrl") or "")
    name = Path(urllib.parse.urlparse(step_url).path).name
    if name:
        return name
    return f"{part['id']}.step"


def step_download_url(part: dict[str, Any], origin: str) -> str:
    step_url = part.get("stepUrl")
    if not step_url:
        raise SystemExit(f"Part {part.get('id', '<unknown>')} does not include stepUrl.")
    return urllib.parse.urljoin(f"{origin_url(origin)}/", str(step_url))


def write_download(part: dict[str, Any], args: argparse.Namespace, allow_requested_filename: bool) -> dict[str, Any]:
    step_url = step_download_url(part, args.origin)

    out_dir = Path(args.out_dir)
    out_dir.mkdir(parents=True, exist_ok=True)
    path = out_dir / filename_for(part, args.filename, allow_requested_filename)
    if path.exists() and not args.overwrite:
        raise SystemExit(f"Refusing to overwrite existing file: {path}")

    data = request(step_url, args.timeout)
    path.write_bytes(data)

    actual_sha256 = hashlib.sha256(data).hexdigest()
    expected_sha256 = part.get("sha256")
    checksum_ok = expected_sha256 is None or expected_sha256 == actual_sha256
    if not checksum_ok:
        raise SystemExit(
            f"Checksum mismatch for {path}: expected {expected_sha256}, got {actual_sha256}",
        )

    return {
        "id": part.get("id"),
        "name": part.get("name"),
        "path": str(path),
        "stepUrl": step_url,
        "pageUrl": part.get("pageUrl"),
        "apiUrl": part.get("apiUrl"),
        "byteSize": len(data),
        "sha256": actual_sha256,
        "checksumVerified": expected_sha256 is not None,
    }


def compact_part(part: dict[str, Any]) -> dict[str, Any]:
    return {
        "id": part.get("id"),
        "name": part.get("name"),
        "category": part.get("category"),
        "family": part.get("family"),
        "standard": part.get("standard"),
        "attributes": part.get("attributes"),
        "stepUrl": part.get("stepUrl"),
        "pageUrl": part.get("pageUrl"),
        "apiUrl": part.get("apiUrl"),
        "sha256": part.get("sha256"),
    }


def main() -> int:
    args = parse_args()
    if args.filename and (not args.download or args.all):
        raise SystemExit("--filename can only be used with --download for one selected part.")
    if not args.part_id and not args.query and not any([args.tag, args.category, args.family, args.standard]):
        raise SystemExit("Provide a query, --id, or at least one facet filter.")

    if not args.download:
        if args.part_id:
            output: Any = compact_part(get_part(args, args.part_id))
        else:
            result = search_parts(args)
            result["items"] = [compact_part(part) for part in result.get("items", [])]
            output = result
        json.dump(output, sys.stdout, indent=2)
        sys.stdout.write("\n")
        return 0

    parts = selected_parts(args)
    downloads = [
        write_download(part, args, allow_requested_filename=len(parts) == 1)
        for part in parts
    ]
    json.dump({"downloads": downloads}, sys.stdout, indent=2)
    sys.stdout.write("\n")
    return 0


if __name__ == "__main__":
    raise SystemExit(main())
````
